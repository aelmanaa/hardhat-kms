A Turnkey transaction that fails after its request reached Turnkey no longer lets the plugin sign its nonce again. This covers a timeout, an abort by a library account's `signal`, an activity that needs approval, a status query that fails, an answer the plugin cannot read, and a signed transaction it refused. Turnkey keeps working on an activity it accepted, and a completed `sign_transaction` activity holds the signed transaction, which every user of the organization can read and broadcast. Before, the next send took the same nonce, so two valid transactions could exist for it. Now the error, `core.signer.transaction-outstanding`, starts with the cause and names the nonce and the activity id, and the network connection's later sends from the account skip that nonce: a gap, never a duplicate. The hold covers `eth_sendTransaction`, `eth_signTransaction` and a library account's `signTransaction`, and ends when a transaction with the nonce reaches the node through the connection, or when the connection closes. These release the nonce as before: a definite refusal by Turnkey (a 4xx answer, or an activity that ended `FAILED` or `REJECTED`), a request that failed before it left, a key with `transactionSigning: "digest"`, and AWS, Google Cloud and Azure keys.

Turnkey also keeps every transaction it signs. A Turnkey transaction that the node refused for certain, for example for insufficient funds, now fails with `core.tx.refused-provider-copy`, which names the nonce and the node's answer, and the nonce stays held: Turnkey's copy becomes valid once the cause goes away. `eth_signTransaction` now takes the nonce a send would take, past the account's earlier sends and held nonces, instead of the node's pending count, and with a Turnkey key holds its own nonce until a transaction with it reaches the node through the connection.

A send that waited for its account's earlier send, or for the plugin's look-up of an unanswered transaction, while its connection closed now fails with `core.tx.connection-closed` before it asks the provider to sign. Before, it signed and then refused to broadcast, which with Turnkey left a signed transaction behind.

Provider plugins get three optional members: `KmsKeyAdapter.signTransactionOutlivesAbort`, for a provider that may still sign a transaction after the plugin gave up on it; `SignContext.requestSent`, which such an adapter calls when its request may have reached the provider; and `SignContext.requestRefused`, which it calls when the provider refused the request for certain. `@hardhat-kms/turnkey` sets the flag for keys that sign with `sign_transaction`.

What should I do? If a Turnkey send fails with `core.signer.transaction-outstanding`, open the activity the message names in the Turnkey dashboard before you send anything else from the account. Reject it while it is pending; then, or if it completed, send a replacement transaction with the nonce the message names. If you maintain a provider plugin, nothing changes unless your provider keeps signing a transaction after the call ends and stores the result where others can broadcast it; then set `signTransactionOutlivesAbort` and call `ctx.requestSent` and `ctx.requestRefused`, as the provider guide describes.
