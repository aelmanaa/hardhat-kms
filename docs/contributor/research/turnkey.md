# Turnkey provider: research and design

Audience: contributors working on the Turnkey provider ([#54](https://github.com/aelmanaa/hardhat-kms/issues/54)), and reviewers who want to know why it works as it does. Assumes the [provider contract](../providers.md) and the [signing pipeline](../signing-pipeline.md). Does not assume Turnkey knowledge.

Status: the research and design as written on 2026-10-15 and 2026-10-16, before the code, with the decisions taken on 2026-10-17 in [section 7](#7-decisions). Every "verified" fact was read in Turnkey's docs or source on those dates; nothing was run against the live Turnkey API. Where the shipped code differs from the design, a note says so. The largest difference: D3 planned digest-only transactions for 1.2 and `sign_transaction` for a later minor; both shipped in 1.2.0, with `sign_transaction` as the default and the digest behind `transactionSigning: "digest"`. The table in section 3.3, D3 and section 9 describe the plan, not what shipped. The user-facing result is [Set up a Turnkey wallet account](../../user/guides/turnkey-setup.md); the decision records are [0019](../decisions/0019-turnkey-without-sdk.md) and [0020](../decisions/0020-turnkey-approvals-fail-fast.md).

It corrects the original issue text, which said that Turnkey has no public-key call. Turnkey returns `publicKey` on wallet accounts and private keys (`get_wallet_account`, `list_wallet_accounts`, `get_private_key`). What it lacks is a lookup by address alone: `get_wallet_account` needs a `walletId`. The address-pinned design holds for that reason.

## 1. Problem

Teams that keep their deployer or operator keys in Turnkey cannot use them from Hardhat 3 through hardhat-kms. They use `@turnkey/viem` or `@turnkey/ethers` in scripts instead, which trust Turnkey's `v` and skip the plugin's checks (address pin, signature recovery, chain-id checks, no bare digest over RPC). Foundry users already have `cast --turnkey`. The plugin should sign with a Turnkey key with the same guarantees as the AWS, Google Cloud and Azure keys.

## 3. Design

### 3.1 Package

`@hardhat-kms/turnkey` in `packages/hardhat-kms-turnkey`, laid out like `@hardhat-kms/azure` (decision 0015). Its `kms` handler claims `provider: "turnkey"` keys, calls `checkProviderVersion`, and loads the adapter with a dynamic `import()`.

Transport: three options; this design recommends (c).

- (a) `@turnkey/http`. Typed request bodies, but no `AbortSignal` (F19), 19 MB, and its retry and polling helpers throw on consensus.
- (b) `@turnkey/api-key-stamper` plus our own `fetch`. Keeps Turnkey's stamping code, adds `@turnkey/crypto` and its pinned dependencies.
- (c) No Turnkey dependency. Stamp with `node:crypto` (P-256, SHA-256, DER, hex, JSON, base64url, as F9 specifies, about 40 lines) and call `fetch` with the key's `signal`. Zero dependencies, full control of abort, redirects, retries and error parsing. The cost: we own a small protocol implementation. A unit test checks our stamp against `@turnkey/api-key-stamper` as a devDependency: each side's stamp must verify with the other's verifier.

(c) departs from decision 0009 ("each package depends on its SDK"), so it needs a decision record. With (b), `@turnkey/*` joins `CLOUD_SDK` in `scripts/test-sdk-floors.ts` and the Dependabot group; its 0.x range `^0.6.17` already stays within 0.6.

### 3.2 Key config

<!-- docs-check: skip -->

```ts
kms: {
  keys: {
    deployer: {
      provider: "turnkey",
      organizationId: configVariable("TURNKEY_ORGANIZATION_ID"), // or a literal UUID
      address: "0x...",                                          // required: signWith and the pin
      apiPrivateKey: configVariable("TURNKEY_API_PRIVATE_KEY"),  // config variable only
      apiPublicKey: configVariable("TURNKEY_API_PUBLIC_KEY"),    // optional
      timeoutMs: 30_000,                                          // optional, common field
    },
  },
}
```

- `organizationId`: the organization or sub-organization that holds the account. Literal or config variable (`identifierSchema`), checked as a UUID. Masked as `<VAR_NAME>` when it comes from a variable.
- `address`: required for Turnkey. It is both what the adapter sends as `signWith` (checksummed, as alloy sends it) and the core's pin. The core recovers the public key from the first signature and checks it against this address (`providers.md`, "Turnkey-style API signer").
- `apiPrivateKey`: only a configuration variable. The schema uses `configurationVariableSchema` from `@nomicfoundation/hardhat-zod-utils` alone, not `sensitiveStringSchema`, so a literal key in the config fails validation. Hardhat resolves it from the environment or `hardhat-keystore`. It is never printed, logged or put in an error.
- `apiPublicKey`: optional. The adapter derives the public key from the private key (as Foundry does, F20). When given, it must match the derived key, or the adapter fails with a clear local error before any request ("the API public key does not match the API private key"), instead of a 401.
- `pinnedId`: the checksummed address. `displayId`: `turnkey:<organizationId or <VAR>>/<address>`.
- Not in config: `baseUrl`. Tests inject it through the adapter factory. A user-settable URL would add an `https` rule and a phishing surface for little gain. Decision D5 (section 7).
- `signWith` by private key id: out of scope; an Ethereum private key also has an address, which works as `signWith` (F2).

The descriptor lives in the core, as for the other providers, so `provider: "turnkey"` is validated even without the package installed, and the missing-package error names `@hardhat-kms/turnkey`.

### 3.3 Signing

| Core request                                                       | Adapter method                          | Turnkey call                                                                                       | What Turnkey policies see                                                                                    |
| ------------------------------------------------------------------ | --------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Transactions, `kms sign-tx`, `kms sign-auth`, `kms sign --no-hash` | `signDigest`                            | `sign_raw_payload`, `HEXADECIMAL`, `NO_OP`, payload = 32-byte digest hex                           | `activity.params.hash_function`, `encoding`, `wallet_account`; no transaction fields                         |
| `personal_sign`, `eth_sign`, `kms sign`                            | `signMessage`                           | `sign_raw_payload`, `HEXADECIMAL`, `KECCAK256`, payload = the EIP-191 prefixed bytes               | The same, plus the preimage is in Turnkey's activity record. Turnkey's policy language has no message struct |
| `eth_signTypedData_v4`, `kms sign --data`                          | `signTypedData`                         | `sign_raw_payload`, `EIP712`, `NO_OP`, payload = serialized typed data                             | `eth.eip_712.{primary_type,domain,message}`                                                                  |
| Phase 2: transactions                                              | `signTransaction` (planned core method) | `sign_transaction`, `TRANSACTION_TYPE_ETHEREUM`, `unsignedTransaction` = the core's unsigned bytes | `eth.tx.*`, including `chain_id`, `to`, `value`, ABI-decoded calls                                           |

As shipped in 1.2.0, the last row is the default for transactions and `kms sign-tx` (`signTransaction` is a core method since [#514](https://github.com/aelmanaa/hardhat-kms/issues/514)). The first row's transactions apply only to a key with `transactionSigning: "digest"`.

Each sign builds a fresh `timestampMs`. The adapter reads the response as follows:

1. HTTP 2xx and JSON. Check `activity.organizationId` equals the configured organization and `activity.type` is the type it sent. A mismatch fails (`turnkey.sign.response-mismatch`), as Azure checks the `kid`.
2. `COMPLETED`: read `result.signRawPayloadResult.{r,s,v}`. `r` and `s` must be 1 to 64 hex characters; `v` must be `00` or `01` (or the 27/28 forms, hex `1b`/`1c`). Anything else fails as `turnkey.sign.malformed`. Return `{ r: BigInt, s: BigInt, yParity: v }`; the core ignores `yParity` and derives the parity.
3. `PENDING` or `CREATED`: poll `get_activity` (a query: no new signature) every 500 ms, then backing off to 2 s, until a terminal status or until the signal aborts. Show `displayMessage("waiting for Turnkey to finish the activity")` once after the first poll.
4. `CONSENSUS_NEEDED` or `AUTHENTICATORS_NEEDED`: fail at once with `turnkey.activity.approval-needed` (see 3.7).
5. `FAILED` or `REJECTED`: fail with `turnkey.activity.failed` or `turnkey.activity.rejected`, with the activity's failure code when it matches the safe-code pattern, never its message.

Phase 2 (`signTransaction`): Turnkey returns the signed RLP. The adapter decodes it, takes only `r`, `s`, `yParity`, and returns them as `SignatureOutput`. The core applies them to its own unsigned transaction and verifies them against its own digest, so Turnkey cannot change what gets broadcast: a signature over a different body does not verify.

What still runs in the core, unchanged, for every Turnkey signature (decision 0004, `signing-pipeline.md`): strict parse and range check of `r` and `s`, low-s normalization (F7: Turnkey's behaviour is unknown), trial recovery against the pinned address, and the final verifier for transactions, EIP-191 and EIP-712. The typed-data `domain.chainId` check and the "no bare digest over RPC" rule (decision 0003) apply before the adapter is called. With EIP-712 encoding Turnkey hashes the typed data itself; if its hash differs from the core's, recovery fails and the core refuses the signature. It never releases it.

### 3.4 Retries and idempotency

- Transport failures (no response, 5xx, 429 `RATE_LIMIT_EXCEEDED` or a 429 without a code): resend the same body, which carries the same `timestampMs`, so Turnkey returns the same activity and makes no second signature (F14). A new stamp is fine: the fingerprint covers the body only. Backoff from 250 ms, doubling, with jitter, at most 4 attempts, always inside the signal.
- No retry for `SIGNING_QUOTA_EXCEEDED`, 400, 401, 403 or 404.
- The core's "one fresh attempt" after an invalid signature calls `signDigest` again. That call builds a new `timestampMs`, so it is a new activity and a second billed signature. If Turnkey's nonce is deterministic (unverified), it returns the same signature and fails the same way, which is correct.

### 3.5 Credentials and secrets

- The API private key reaches the adapter only through a resolved config variable. Locally it comes from `hardhat-keystore` or the environment; in CI from a secret exposed as `TURNKEY_API_PRIVATE_KEY`.
- The setup guide tells users to create a dedicated non-root API-only user, with a policy that allows only `SIGN_RAW_PAYLOAD` (and later `SIGN_TRANSACTION`) on the one wallet account, and an API key with `expirationSeconds` for CI (F10, F12). A root user's key bypasses every policy; the guide says so.
- Passkeys and the session flows (F11) are out of scope: they need a browser or an authenticator.
- Debug output: method, status, activity status, timings, `turnkeyErrorCode`. Never the body, the `X-Stamp` header, the organization id, the activity id or Turnkey's message. Add the API private key and public key to the planted-secret test in `test/integration/debug.test.ts`.

### 3.7 Timeout, abort and approvals

- Every request and every poll uses `ctx.signal`, so the key's `timeoutMs` (default 30 s) bounds the whole sign, polling included. On abort, the core reports `core.signer.no-answer` or `core.signer.cancelled` as it does for every provider.
- An abort after Turnkey accepted the activity leaves that activity in Turnkey. Its result, the signature, stays readable by any user of the organization: all users have implicit read access (F12). This matches the existing note that "the request may still complete at the provider".
- Consensus does not fit the model. An approval takes minutes to 24 hours (F13), while an RPC call such as `eth_sendTransaction` from viem or ethers blocks the script, and the plugin fills the nonce before it signs (decision 0002). The MVP therefore fails fast on `CONSENSUS_NEEDED` with a message that the key's policy needs approval, and that the activity stays pending in Turnkey until someone approves or rejects it.
- The pending activity is a risk. If an approver later approves it, the signature exists for a transaction the plugin gave up on, with a nonce the plugin may reuse. For a `sign_transaction` activity (phase 2), the result is a ready-to-broadcast signed transaction. The guide must say: reject the pending activity in the dashboard. Whether the requesting API user can reject its own activity through `ACTIVITY_TYPE_REJECT_ACTIVITY` is unverified; if it can, a follow-up rejects it on abort.
- Follow-up, not in v1.2: an opt-in wait mode for keys with consensus (a per-key `approval.waitMs`, a `displayMessage` with the activity's dashboard location, polling at a slow rate, reject on abort). #177 removed `approvalTimeoutMs` before 1.0 so that it could come back as an additive field; this is that case.

### 3.8 What does not fit, and non-goals

- Waiting for human approval (3.7). Fail fast in v1.2.
- Turnkey's broadcast and gas sponsorship (`eth_send_transaction`, `broadcast_evm_transaction`): Turnkey fills the nonce and gas itself, which conflicts with the plugin filling transactions (decision 0002). This matches the planned `sendTransaction` of #55, not #54.
- Passkey, OTP, OAuth and session credentials.
- `kms history`: Turnkey has `list_activities` (swagger path verified; its filters unverified). A reader is a follow-up.
- `--kms turnkey` on the command line (decision 0008 excludes it).
- Raw signing for non-EVM curves, `sign_raw_payloads` batches, private-key-id `signWith`, import or export of keys.
- EIP-7702 authorizations through `PAYLOAD_ENCODING_EIP7702_AUTHORIZATION` (would let policies see `eth.eip_7702_authorization`): needs a `signAuthorization` adapter method. Follow-up.
- `getPublicKey` or `getAddress`. With a required `address`, the core needs neither. `kms address` then reports the address as unconfirmed until the first signature. A follow-up can add an optional `walletId`, read `get_wallet_account`, decompress the public key if needed (F8), and let the core confirm the pin before signing.

Table notes:

1. `--kms turnkey` is the env-only path a Foundry user would look for. Decision 0008 excludes it, and 3.8 keeps it a follow-up. The migration path for v1.2 is a config entry that reads Foundry's three variable names, with the address written as a literal (Note 2). The setup guide should show that entry.
2. In Foundry the address comes from the same environment as the API key, so whoever can change one can change the other, and nothing checks the address. Here the pin is a literal in the config, like every other provider's `address` (`docs/user/reference/configuration.md:130`), and the core checks it by recovery. A Foundry user who keeps `TURNKEY_ADDRESS` in CI variables has to move the address into the config.
3. Foundry sends a digest for every request, so a Turnkey policy written for Foundry can be as narrow as `activity.params.hash_function == 'HASH_FUNCTION_NO_OP'` on one account. Under this design, messages (`KECCAK256`) and typed data (`EIP712`) do not match such a policy and fail with 403, while transactions pass. The reverse also holds: an organization that denies `NO_OP` blocks all of Foundry but only transactions here (D3). There is a privacy side too: with D4, the message preimage is stored in Turnkey's activity record, readable by every user of the organization (F12). Foundry sends only the hash. D8 covers the policy part.
4. alloy is stricter on padding (exactly 32 bytes) and looser on `v` (EIP-155 forms) than the design. Neither matters much here, because the core range-checks `r` and `s` and never uses `v`. If the live smoke test shows `r` and `s` are always 64 hex characters (F6, unverified), the adapter can require that too, as alloy does.
5. The design retries because of the 1 RPS limit on Free and Pay-as-you-go (F15), and because resending the same body makes no second signature (F14). It never quotes Turnkey's message, because it can name organizations (F16). Foundry users will see fewer transient failures and shorter error text.
6. Foundry's listing prints the variable without calling Turnkey, so it succeeds with a wrong key or organization. The comparison page says `kms accounts` "checks access", which a Turnkey key cannot do without a signature (no `getPublicKey`, 3.8). The design should say that `kms accounts` lists the pin as unconfirmed for a Turnkey key, as `kms address` does. How the core's `kms accounts` treats an adapter without `getPublicKey` today: unverified. Since checked in the code: the core lists such a pin as `not checked` (`packages/hardhat-kms/src/internal/tasks/accounts.ts`).

What Foundry does that the design left out:

- It puts the activity id in the consensus error. The design forbids the id in output (3.5), yet asks the user to find and reject the pending activity (3.7). D9.
- `cast wallet list --turnkey` and `cast wallet address --turnkey` work offline. The design covers `kms address` (3.8) but not `kms accounts` (Note 6).

What Foundry users may find surprising in the design:

- No `--kms turnkey`; a config entry is needed, and the address moves from `TURNKEY_ADDRESS` into the config (Notes 1 and 2).
- A policy that allows only `NO_OP` denies messages and typed data (Note 3, D8).
- Message text is visible in Turnkey's activity log (Note 3, D4).
- `organizationId` must be a UUID (P6).
- Typed data whose `domain.chainId` differs from the network's chain is refused unless `--allow-cross-chain` is given (P17).
- A signature from Turnkey that does not recover to the address is refused, where Foundry would print or broadcast it (P15).

## 5. Test strategy

There is no emulator (F18), so the tests replace Turnkey with a local HTTP stub.

- Unit (`test/unit/`), with an injected `fetch`:
  - the stamp: format, base64url, DER, and a cross-check with `@turnkey/api-key-stamper` both ways;
  - body shapes for each method (`signWith`, `encoding`, `hashFunction`, `timestampMs` as a string);
  - `COMPLETED`, `PENDING` then `COMPLETED`, `CONSENSUS_NEEDED`, `AUTHENTICATORS_NEEDED`, `FAILED`, `REJECTED`;
  - every catalogue row from a canned error body; the 429 code split (quota against rate limit);
  - 3xx refused;
  - malformed `r`/`s`/`v`;
  - wrong organization or activity type in the response;
  - retries resend the identical body; the "fresh attempt" sends a new `timestampMs`;
  - abort mid-request and mid-poll;
  - the public-key mismatch check.
- Integration (`test/integration/`): a `node:http` stub of `/public/v1/submit/sign_raw_payload`, `/public/v1/submit/sign_transaction` and `/public/v1/query/get_activity`. The stub verifies each `X-Stamp` with the configured P-256 public key, signs with a noble secp256k1 test key, and hashes EIP-712 payloads with the core's vendored encoder. It can return high-s values, a wrong `v`, or a signature from another key, so the core's checks run end to end through a real Hardhat runtime: RPC accounts, `kms` tasks, viem and ethers deploys. Plus the import test (loading a config loads no Turnkey code) and `package-name.test.ts`.
- Recordings: not recommended as the main fixture. Stamps are random and `timestampMs` changes, so a replay must ignore both. Capture one real response per activity status during the first live run, scrub ids, and use it to shape the stub.
- Live (`test/live/turnkey.live.test.ts`, skipped unless `HARDHAT_KMS_LIVE_TURNKEY_ADDRESS` and the two credentials are set):
  - Smoke: about 6 signatures (message, typed data, digest, one legacy and one EIP-1559 transaction on the fork, one EIP-7702 authorization), plus a denied request (a second address the policy does not allow) to pin the 403 mapping, and the consensus case against a second wallet account under a 2-approver policy.
  - The full Sepolia matrix runs about 39 cases. Count the signatures per run before enabling it (estimate: 40 to 60, so $4 to $6 a run on Pay-as-you-go).

What a maintainer sets up for live tests, once:

1. A Turnkey dashboard account and a dedicated test organization. It needs an email address separate from any production account (F17).
2. A wallet with one Ethereum account, and a second account for the denied and consensus cases.
3. A non-root API-only user. Generate its P-256 key pair locally (Turnkey CLI or dashboard) with an expiry, for example 90 days.
4. Two or three policies (the Free plan allows 5): allow `SIGN_RAW_PAYLOAD` and `SIGN_TRANSACTION` for that user on account 1; require `approvers.count() >= 2` on account 2.
5. Repository secrets for `TURNKEY_API_PRIVATE_KEY` and `TURNKEY_ORGANIZATION_ID`; the address as a variable. Fund the address with Sepolia ETH for the Sepolia run.

Cost: the Free plan's 25 signatures a month cover about 3 smoke runs. Release runs with the Sepolia matrix need Pay-as-you-go: a card, $0.10 a signature, roughly $5 to $15 a month at the current release rate (estimate).

## 7. Decisions

- D1. Transport: no Turnkey dependency with our own stamper (recommended), or `@turnkey/api-key-stamper`, or `@turnkey/http`. Option (c) needs a decision record that amends 0009.
- D2. Consensus in v1.2: fail fast (recommended), or ship the wait mode now.
- D3. Transactions in v1.2: digest only, so Turnkey policies cannot see transactions, then `signTransaction` in a v1.2.x minor (recommended); or hold v1.2 until `signTransaction` lands. A team that sets a policy denying `HASH_FUNCTION_NO_OP` cannot send transactions until then.
- D4. Messages: send the EIP-191 preimage with `KECCAK256` (recommended: Turnkey's record shows what was signed), or the digest with `NO_OP`, as `@turnkey/viem` does.
- D5. `baseUrl` in config: test-only injection (recommended), or a user-facing field restricted to `https`.
- D6. Live budget: Free plan with the smoke test only, or Pay-as-you-go so the Sepolia matrix and `live-proof.md` include Turnkey.
  - **Chosen on 2026-10-17: Free plan.** 25 signatures a month. Consequences: the live smoke test (about 8 to 10 signatures) runs only for releases that change Turnkey code, at most about twice a month; Turnkey is not in the nightly run or the full Sepolia matrix, and `live-proof.md` marks it "smoke only". The integration stub carries the edge cases. The live test counts its signatures and stops before 12 per run, and a quota 429 is reported as `turnkey.service.quota`, not as a failure of the plugin. Revisit if users report Turnkey bugs the stub missed.
- D7. Make `address` required (recommended), or also accept `walletId` and fetch the public key now.
- D8. Turnkey policies written for Foundry (Foundry parity, Note 3). Foundry sends a `NO_OP` digest for everything, so a policy that allows only `NO_OP` denies this design's messages and typed data. Options: (a) keep D4 and the `EIP712` encoding; the setup guide gives one policy that allows all three request shapes, and the 403 message for a message or typed-data request names the encoding it used (recommended); (b) also add a per-key option that signs everything as a `NO_OP` digest, as Foundry does, for teams that share one key and one policy between the two tools; (c) on a 403, retry as a digest. (c) is not recommended: it quietly gets around a policy the organization chose.
- D9. Activity id in the consensus error. Foundry prints it; 3.5 keeps it out of all output. The user needs it to find and reject the pending activity (3.7). Put the activity id in the `turnkey.activity.approval-needed` message only (recommended; it is an opaque id that identifies no organization), or keep it out and tell users to search the dashboard by time.
- Shipped: D3 changed before the release. 1.2.0 signs transactions through `sign_transaction` by default ([#515](https://github.com/aelmanaa/hardhat-kms/issues/515)), and keeps the digest for a key with `transactionSigning: "digest"`, which also covers D8's option (b) for transactions.
- **Chosen on 2026-10-17: D1 to D5 and D7 to D9 as recommended** (own stamper, no Turnkey dependency; fail fast on consensus; digest-only transactions first, `signTransaction` in a later minor; messages as preimage with `KECCAK256`; `baseUrl` test-only; `address` required; Foundry-style policies handled by the guide policy and a 403 that names the encoding; activity id in the approval-needed error only). D6: Free plan (above).

## 8. Risks

- Owning the stamp code (D1). Mitigation: the cross-check unit test against Turnkey's stamper, and the live smoke test before each release.
- Turnkey changes response shapes or status codes. Mitigation: a strict parse that fails closed, and the core's verification, which refuses any signature that does not recover to the address.
- High-s signatures (F7): handled by the core's normalization; the live test records whether any appear.
- Pending activities approved after the plugin gave up (3.7): a double signature for one nonce. Mitigated by fail-fast, the guide, and reject-on-abort if the API allows it.
- Root-user API keys bypass policies; the plugin cannot see whether a key is root. Mitigation: the guide.
- A long-lived P-256 key in CI, with no keyless federation as AWS, Google Cloud and Azure have. Mitigation: key expiry, least-privilege policy, rotation steps in the guide.
- 1 RPS on Free and Pay-as-you-go: a deploy script that signs in parallel, with polling, hits 429s. Retries with backoff absorb short bursts; the guide names the limit.
- Cost and quota for live tests (D6).

## 10. Not verified

- Whether Turnkey returns low-s signatures, and whether its ECDSA nonce is deterministic.
- Whether `r` and `s` are always 64 hex characters (left-padded).
- The encoding of `publicKey` on wallet accounts (compressed or uncompressed).
- Whether `signWith` matching is case-sensitive for addresses (alloy sends the checksummed form).
- The exact `turnkeyErrorCode` for stale timestamps, and for an address not in the organization.
- Whether denied or failed sign activities count toward the signing quota.
- Whether an API user can reject its own pending activity.
- Whether a parent organization's API key can sign for a sub-organization's wallet, and under which policies.
- Real latency of a synchronous sign activity (no live call was made).
- The filter fields of `list_activities` for a history reader.
- Whether every Turnkey organization id is a UUID (Foundry accepts any string).
- How `kms accounts` treats a key whose adapter has no `getPublicKey` (Foundry parity, Note 6). Answered since: it lists the pin as `not checked` without calling the provider, and `--check-sign` confirms it with one signature.
- On Foundry's side: whether reqwest's default redirect policy resends the body and `X-Stamp`, and how `turnkey_client` 0.7.0 reports `AUTHENTICATORS_NEEDED` (read, not run).
