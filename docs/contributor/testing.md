# Testing

Audience: Contributors writing or running tests.

Status: M1 adds the signing core's unit tests: crypto vectors and properties, the signer against a fake adapter, and byte equivalence with Hardhat's message and typed-data vectors. M3 adds the AWS adapter's tests in `packages/hardhat-kms-aws/test`, and M6 the Google Cloud and Azure adapters' in `packages/hardhat-kms-gcp/test` and `packages/hardhat-kms-azure/test` ([#29](https://github.com/aelmanaa/hardhat-kms/issues/29), [#30](https://github.com/aelmanaa/hardhat-kms/issues/30)). M4 adds the network hook's integration tests ([#19](https://github.com/aelmanaa/hardhat-kms/issues/19)), and M5 the deploy tests with hardhat-viem, hardhat-ethers and Ignition ([#26](https://github.com/aelmanaa/hardhat-kms/issues/26)). The other tests arrive with their milestones.

## Testing strategy

Tests form a pyramid. The lower layers are fast and pure; the upper layers exercise real SDKs and real chains.

1. Unit tests for pure crypto:
   - Vectors for SPKI DER/PEM, JWK with stripped zeros, the wrong curve, and DER strictness.
   - fast-check properties: high-S and low-S DER both normalise and recover to the address; parsing random bytes never succeeds silently; JWK and SPKI encodings convert back and forth without loss.
   - CRC32C vectors.
   - The vendored EIP-712 code checked against the package's `verifyTyped`.
2. Unit tests for the signer and adapters:
   - Injected fake SDK clients sign with a local key and return the exact wire formats: AWS SPKI + DER; GCP PEM + DER + CRC (including corrupted CRCs); Azure JWK + r‖s.
   - Assertions on request parameters: `MessageType: DIGEST`, the ARN taken from `GetPublicKey`, `ES256K` with the versioned id, the GCP call options.
   - A fake adapter that returns a signature from the wrong key, and an address-pin mismatch.
   - An AbortSignal timeout, driven by an injected clock.
   - The signer cache (`packages/hardhat-kms/test/unit/signer/key-cache.test.ts`): one signer per key, failures not kept, the idle close after the last connection and re-creation on next use, driven by injected timers.
   - Bounded GCP CRC retries, and the Azure managed identity timeout.
   - The AWS adapter's tests are in `packages/hardhat-kms-aws/test/unit/adapter.test.ts`, with the fake SDK in `packages/hardhat-kms-aws/test/helpers/fake-aws-kms.ts`.
   - The Azure adapter's tests are in `packages/hardhat-kms-azure/test/unit/adapter.test.ts`, with the fake SDK in `packages/hardhat-kms-azure/test/helpers/fake-key-vault.ts`. They cover `EC` and `EC-HSM` JWKs, coordinates without leading zeros, wrong key types and curves, disabled, expired and not-yet-valid keys, a sign response whose `kid` names another version, a signature of the wrong length, and the errors for 401, 403, 404 and a missing credential. `packages/hardhat-kms-azure/test/unit/credential.test.ts` checks the credential chain's order, the managed identity timeouts, the managed identity left out where it refuses a client id, and the token sharing, with a fake `@azure/identity`. `packages/hardhat-kms-azure/test/integration/managed-identity-exit.test.ts` runs the real chain in a child process with no `az` or `azd` on `PATH` and `AZURE_POD_IDENTITY_AUTHORITY_HOST` pointing at a local endpoint that accepts connections and never answers, and fails unless the process exits on its own within 25 seconds.
   - The Google Cloud adapter's tests are in `packages/hardhat-kms-gcp/test/unit/adapter.test.ts`, with the fake SDK in `packages/hardhat-kms-gcp/test/helpers/fake-gcp-kms.ts`. Like Cloud KMS, the fake confirms `verifiedDigestCrc32c` only when the `digestCrc32c` it receives matches the digest. The tests corrupt or drop each of `pemCrc32c`, `verifiedDigestCrc32c` and `signatureCrc32c`: two bad answers are retried and pass, a persistent fault fails after four attempts, and an aborted call stops retrying. They also cover a response for another key version (no retry), a wrong algorithm, the gax `timeout` and the client's `fallback: true`, and the message for each gRPC status, which never repeats the server's text. `packages/hardhat-kms-gcp/test/unit/wire.test.ts` covers the `Int64Value` forms and status codes.
3. Byte equivalence:
   - A deterministic fake backend (RFC6979 with Hardhat's test key) must produce raw transactions and signatures byte-identical to Hardhat's `local-accounts.ts` vectors: legacy, 2930, 1559, 7702, eth_sign, personal_sign, 712.
   - Differential checks against viem `signTransaction` and ethers `Wallet.signTransaction`.
   - The differential fill test described under [Transaction filling](transactions.md#transaction-filling), run against the Hardhat floor and `latest`. `pnpm run test:hardhat-versions` (`scripts/test-hardhat-versions.ts`) runs two test files, `transaction-filler.test.ts` and `network-hook.test.ts`, on the floor of the `hardhat` peer range and on the newest 3.x release that is at least a day old (or older than `minimumReleaseAge`, if the project sets one). The one-day hold is deliberate: pnpm's built-in default would install a younger release and add it to `minimumReleaseAgeExclude`, which this repository never does, so a younger release is held back and tested by the next weekly run. For each version the script sets the `hardhat` catalog entry in `pnpm-workspace.yaml`, installs, checks that hardhat-kms resolves it, builds, typechecks and runs the tests, then restores `pnpm-workspace.yaml` and the lockfile, also on Ctrl-C. A failure names the Hardhat version and the stage that failed (install, build, typecheck or tests); a failing fill test names the fill step. The `hardhat-versions.yml` workflow runs it weekly, on demand, and on pull requests that change the paths listed in that workflow; it is not a required check.
4. Integration tests on a real HRE with `edr-simulated` and a fake adapter registered through the `kms` hook:
   - The network hook (`packages/hardhat-kms/test/integration/network-hook.test.ts`), on an `edr-simulated` network and an unreachable http network: account listing (own accounts first, pinned addresses without a KMS call, duplicates listed once, KMS addresses only when the downstream call fails); `personal_sign`, `eth_sign` and `eth_signTypedData_v4` matching Hardhat's local-account vectors; pass-through for other addresses and methods; strict hex and malformed typed data refused before any KMS call; transactions from KMS accounts refused; adapter-creation errors reduced to the error class; two keys for the same account refused; the `default`-network warning printed once; networks without KMS keys left alone.
   - Unknown accounts (`packages/hardhat-kms/test/integration/unknown-account.test.ts`): `eth_sendTransaction`, `personal_sign` and `eth_sign` from an address that is neither a KMS account nor a local account fail with the KMS address appended, on an `edr-simulated` network (`ProviderError`, -32000), on an http network with local accounts (Hardhat's HHE716, whose `formattedMessage` carries the list for the CLI), on an http network without them (the node's error answer, including Geth's `unknown account`) and on a network whose `from` is unknown. The error keeps its class, code and data, shows through viem and ethers, and names no key. A local account's errors, and errors not about the account, stay exactly as on a network without KMS keys. 10, 11 and 12 KMS accounts list all 10, then "and 1 more" and "and 2 more". A plugin listed before hardhat-kms throws a frozen error, partly writable errors and the same error twice: the error comes back as it came, or with the list once. `packages/hardhat-kms/test/unit/rpc/unknown-account.test.ts` covers which errors match, including Reth's and Anvil's -32602 answers, and the sentence itself.
   - On-chain verification (`packages/hardhat-kms/test/integration/ecrecover.test.ts`): the fixture project `packages/hardhat-kms/test/fixture-projects/ecrecover` compiles `Recover.sol`, which recovers a signer with `ecrecover` and refuses high-S signatures, as OpenZeppelin's ECDSA does. Through `@nomicfoundation/hardhat-viem` and `@nomicfoundation/hardhat-ethers`, messages and typed data signed by a KMS account whose fake KMS returns only high-S signatures must recover to that account on chain, with one KMS signature per request, so a retry cannot hide a signature the plugin failed to normalize. Typed data for another chain is refused.
   - Deploys (`packages/hardhat-kms/test/integration/deploy.test.ts`): the fixture project `packages/hardhat-kms/test/fixture-projects/deploy` compiles `Counter.sol`, whose constructor takes arguments and records the deployer as owner, and whose `add` only the owner can call, so a successful call shows which account sent it. The project's `ignition/modules/Counter.ts` deploys it and calls `add`. The KMS keys are not EDR's default accounts, so EDR cannot sign for them; one fake KMS returns only high-S DER signatures and another low-S compact ones, and each test checks the number of KMS signatures, one per transaction. `kms.simulatedBalance` funds the KMS accounts. The tests cover:
     - hardhat-viem: `sendDeploymentTransaction` and `deployContract` with a KMS wallet client, a write, the state read back, and `from` on the receipts.
     - hardhat-ethers: the same through `ethers.getSigner(kmsAddress)`.
     - Ignition, through `@nomicfoundation/hardhat-ignition-viem`: `ignition.deploy` with a KMS `defaultSender` on a network that also has local accounts; a module that picks the KMS account with `m.getAccount(index)` next to a contract from the local default sender; the first KMS account as default sender on a network with `accounts: []`; and the `ignition deploy` task with `defaultSender`.
     - Local and KMS accounts on one network: `eth_accounts` and `ethers.getSigners()` list EDR's 20 accounts first, then the KMS accounts; one script deploys and writes from a local account and from a KMS account, and the local account cannot write to the KMS account's contract.
     - `--kms`: a runtime created with `{ kms: "aws", network }` and `AWS_KMS_KEY_ID` set, a fake adapter for that key, the key funded by `kms.simulatedBalance`, and a deploy and write through viem from it.
   - Other signing plugins ([`packages/hardhat-kms/test/integration/ledger.test.ts`](../../packages/hardhat-kms/test/integration/ledger.test.ts)): hardhat-kms and hardhat-ledger in both `plugins` orders. The tests check the account lists, that the KMS account's `personal_sign` and `eth_sendTransaction` are signed by hardhat-kms, that the Ledger account's requests reach hardhat-ledger's connect step without a device, and that a transaction without `from` succeeds only with hardhat-ledger listed first ([Other signing plugins](architecture.md#other-signing-plugins)).
   - hardhat-viem and hardhat-ethers flows: deploy, every transaction type, and `signMessage`/`signTypedData` verified on chain with `ecrecover`.
   - Sends (`packages/hardhat-kms/test/integration/send-lock.test.ts`): 10 parallel sends from each of two KMS accounts on an `edr-simulated` network, with an `eth_signTransaction` among them, are all mined with nonces 0 to 9 per account, under a 60 s guard against a deadlock. Over HTTP to the recording node, whose pending count never moves, sends get consecutive nonces; a broadcast that times out under hardhat-viem reaches the node once and fails with -32000; a retried request after a broadcast without an answer sends the same bytes, without a new KMS signature, and returns the same hash; a node's refusal comes back unchanged. On a simulated network, a reverted send throws Hardhat's `SolidityError` with its revert data and transaction hash. `packages/hardhat-kms/test/unit/rpc/send-lock.test.ts` covers the same rules through the network hook with a fake node and fake timers, as [Transactions](transactions.md#retries-after-broadcast) describes.
   - Chain-id guards.
   - Config errors reported at the exact path.
   - Every task.
   - `hardhat run` exits (covered for now by the AWS exit test in layer 5).
   - Error messages never contain the injected fake secrets.
5. Provider packages with their real SDK against a local endpoint:
   - `packages/hardhat-kms-aws/test/integration/plugin.test.ts` loads `hardhat-kms-aws` in an HRE and signs through the real `@aws-sdk/client-kms`. The SDK talks to a local HTTP server that speaks the KMS JSON 1.1 protocol (`packages/hardhat-kms-aws/test/helpers/kms-server.ts`). The test checks the `X-Amz-Target` of each request, that `Sign` uses the key ARN from `GetPublicKey` with `MessageType: DIGEST`, and the region in the SigV4 credential scope. It also checks that the handler passes keys of other providers on, and that listing `hardhatKms` and `hardhatKmsAws` together works.
   - `packages/hardhat-kms-aws/test/integration/network.test.ts` opens a connection with `hre.network.create` to a network whose `kmsAccounts` key points at the same local server. It checks that `eth_accounts` lists the key's address, that `personal_sign` returns the signature from Hardhat's own local-accounts tests, and that the server saw one `GetPublicKey` and one `Sign`. It also runs `packages/hardhat-kms-aws/test/fixtures/sign-and-exit.ts` in a child process, which signs without closing the connection, and fails unless the process exits by itself.
   - `packages/hardhat-kms-aws/test/integration/sdk-loading.test.ts` checks that loading a config loads no AWS SDK module, and that creating an AWS adapter does (see [SDK loading](architecture.md#sdk-loading)).
   - `packages/hardhat-kms-azure/test/integration/plugin.test.ts` runs the real `@azure/keyvault-keys` with a fake `HttpClient` (`packages/hardhat-kms-azure/test/helpers/key-vault-http.ts`) that answers the Key Vault REST API in process, including its challenge-based authentication. Key Vault hosts must end in an Azure vault suffix, so the SDK cannot be pointed at a local server; the fake `HttpClient` is the seam instead. The test checks the request paths, that `sign` uses `ES256K` against the version pinned from the first read, and that the adapter reads the `kid` of the real response. `network.test.ts` runs Hardhat's `personal_sign` and `eth_signTransaction` vectors through the network hook with a fake SDK, including high-S signatures and a signature of the wrong length, and runs `test/fixtures/sign-and-exit.ts` with the real SDK to check that the process exits by itself. `sdk-loading.test.ts` checks that no module under `@azure/`, `@azure-rest/` or `@typespec/` loads before an Azure key is used.
   - `packages/hardhat-kms-gcp/test/integration/` does the same for Google Cloud, with the real `@google-cloud/kms` over its REST transport. There is no Cloud KMS emulator, so `packages/hardhat-kms-gcp/test/helpers/kms-server.ts` serves `GetPublicKey` and `AsymmetricSign` over HTTP, checks `digestCrc32c` as Cloud KMS does, and returns high-S signatures. The SDK reaches it through `kmsHandlers(version, sdk)`, registered at run time, with a client subclass that sets the endpoint and a throwaway service account whose self-signed tokens need no network. The tests check the request paths, the base64 digest and its checksum, a retried corrupted `signatureCrc32c`, the messages for NOT_FOUND, FAILED_PRECONDITION and PERMISSION_DENIED, `personal_sign` and `eth_signTransaction` against Hardhat's vectors (so the high S is folded), a signature that is not strict DER, and that `packages/hardhat-kms-gcp/test/fixtures/sign-and-exit.ts` exits by itself.
   - These tests run the SDK version in `pnpm-lock.yaml`. `pnpm run test:sdk-floors` (`scripts/test-sdk-floors.ts`) runs each provider package's tests again with the lowest version of each cloud SDK its range allows: it reads the floor from the caret range in `package.json`, installs that exact version, checks the package resolves it, typechecks the package and its tests against it, and restores `package.json`, `pnpm-workspace.yaml` and the lockfile afterwards, also on Ctrl-C. The `sdk-floors.yml` workflow runs it when a provider package, a manifest, the lockfile, `pnpm-workspace.yaml` or the script changes; it is not a required check. If a floor fails, raise it in the same pull request to a version that passes, and give the reason in the changeset.
6. Emulated AWS: `packages/hardhat-kms-aws/test/localstack/aws-kms.test.ts` starts LocalStack `4.14.0`, pinned by digest and bound to a random port on 127.0.0.1, and runs the real `@aws-sdk/client-kms` through the plugin against keys it creates. Each of 32 signatures must verify and recover to the key; about half come back high-S, and the test fails unless it saw both kinds. An alias moved to another key after the first lookup must keep signing with the first key, a key ARN without a configured region must work, and P-256 and symmetric keys are refused. Real KMS always echoes the key ARN and algorithm and never offers secp256k1 keys for encryption, so the checks on those response fields are covered by the unit tests only. Run it with `pnpm run test:localstack`, which needs Docker. In CI it runs on Ubuntu only, in the `localstack` job.
   - The examples: `packages/hardhat-kms-aws/test/examples/examples.test.ts` runs every project in `examples/` against the same pinned LocalStack image. It creates one `ECC_SECG_P256K1` key and computes its address from the public key with `@noble/curves` and `@noble/hashes`, independently of the plugin. It runs each example unchanged, through pnpm in the example's folder, with `AWS_ENDPOINT_URL_KMS`, `AWS_REGION` and test credentials pointing the AWS SDK at LocalStack and `AWS_KMS_KEY_ID` naming the key. For each example it runs `hardhat build`, `tsc -p .` against the example's own strict `tsconfig.json`, oxlint with `examples/oxlint.json` (the root rules, type-aware, with `no-console` off), and `pnpm run deploy --network rehearsal`, an `edr-simulated` network with `accounts: []` whose only account is the KMS account, funded by `kms.simulatedBalance`. The deploy script prints `Deployer:`, `Counter:`, `Owner:` and `Count:` lines; the test requires the deployer and the contract's `owner()` to be the key's address and the count read back to be 12. For each Ignition module under an example's `ignition/modules/`, it also starts `hardhat node` on port 8545, funds the key's address with `hardhat_setBalance`, runs `hardhat ignition deploy` on the built-in `localhost` network with `--kms aws` and the key's address as `--default-sender`, and reads `owner()` and `count()` back from the node with `eth_call`. A simulated network keeps no state once the task exits, which is why this step uses a node. A new example must print the same four lines. Run it with `pnpm run test:examples`, which needs Docker; in CI it runs in the `examples` job.
   - The examples are pnpm workspace members. Their `package.json` asks for `hardhat-kms` and `hardhat-kms-aws` with the caret range of the current version, as a project installing from npm would, and `linkWorkspacePackages: true` in `pnpm-workspace.yaml` links those ranges to the workspace packages. `changeset version` rewrites the ranges when it bumps the packages, so a copied example never contains `workspace:` or `catalog:`. The new ranges change the lockfile too, so version the packages with `pnpm run version-packages`, which runs `changeset version` and then `pnpm install --lockfile-only`; the version pull request then carries a lockfile that `pnpm install --frozen-lockfile` accepts. Each example also lists its other dependencies with plain version ranges.
7. Live tests use real cloud keys. Today the AWS, Azure and Google Cloud smoke tests exist. `packages/hardhat-kms-gcp/test/live/gcp-kms.live.test.ts`, run with `pnpm run test:live:gcp`, is skipped unless `HARDHAT_KMS_LIVE_GCP_KEY` holds the full name of an `EC_SIGN_SECP256K1_SHA256` key version. It uses the developer's Application Default Credentials, creates nothing, redacts the project, key ring and key names from failures, signs 16 digests with the name and once with the components form, and checks that a missing version fails with a clear message. The Azure one, `packages/hardhat-kms-azure/test/live/azure-key-vault.live.test.ts`, run with `pnpm run test:live:azure`, is skipped unless `HARDHAT_KMS_LIVE_AZURE_KEY_ID` holds the versioned URL of the current version of a `P-256K` key. It signs through the plugin's credential chain (`az login` is enough), creates nothing, redacts the vault, key name and version from failures, and checks that the versioned id, the unversioned id and the components give the same key, and that a version that does not exist fails with 404. The AWS one: `packages/hardhat-kms-aws/test/live/aws-kms.live.test.ts`, run with `pnpm run test:live:aws`, is skipped unless `HARDHAT_KMS_LIVE_AWS_KEY_ID` names an `ECC_SECG_P256K1` key with an alias. It uses the developer's own credentials and region, creates nothing, redacts the key id, ARNs and account ids from every failure it reports, and signs through the plugin with the key id, an alias of the key, and the key ARN with `AWS_REGION` set to another region, where the bare key id must fail with `NotFoundException`. Beyond the guide's policy, the identity needs `kms:DescribeKey` on the key and `kms:ListAliases`, which only accepts the resource `*`. The first run ([#100](https://github.com/aelmanaa/hardhat-kms/issues/100)) used an administrator identity and the default key policy; checking the guide's least-privilege policy against real KMS is part of [#43](https://github.com/aelmanaa/hardhat-kms/issues/43). The full live tests (`pnpm run test:live`) will use real AWS, GCP and Azure keys on Sepolia. A developer runs them locally with their own `aws`, `gcloud` and `az` logins; nothing is stored in the repository, and providers without a configured key are skipped. They deploy, send every transaction type, and verify message and typed-data signatures on chain. Transaction hashes are recorded in `docs/live-proof.md`. Running them in GitHub Actions with OIDC federation is planned before the repository goes public ([#79](https://github.com/aelmanaa/hardhat-kms/issues/79)).
8. Mutation testing runs Stryker (tap-runner) on `crypto/` and `signer/`. It becomes a nightly job after milestone M9.

Test code follows a few conventions:

- Each test opens a fresh connection with `hre.network.create()` (`connect()` is deprecated since Hardhat 3.18; `getOrCreate()` reuses cached connections, so per-connection state must tolerate reuse).
- HRE test files run with `concurrency:false`.
- Test globs are quoted in scripts, so the shell does not expand them.
- Helpers live in each package's own `test/helpers`, because `hardhat-test-utils` is private.
- The root `test`, `test:unit` and `coverage` scripts run `pnpm run build` first, because provider packages import the core from its built `dist/`.

Coverage uses c8 on native TypeScript (Node 24), with a threshold of 95% for lines, branches, functions and statements across each package's `src/`, set in the package's `.c8rc.json`. Provider adapters are tested with fake SDK clients, so they are held to the same bar. `types.ts` and `type-extensions.ts` are excluded.
