# Testing

Audience: Contributors writing or running tests.

Status: every layer below exists: the signing core's unit tests, each adapter's tests in its package, the network hook's integration tests, the deploy tests with hardhat-viem, hardhat-ethers and Ignition, the task tests, and the live tests on Sepolia with their transaction matrix.

## Testing strategy

Tests form a pyramid. The lower layers are fast and pure; the upper layers exercise real SDKs and real chains.

1. Unit tests for pure crypto:
   - Vectors for SPKI DER/PEM, JWK with stripped zeros, the wrong curve, and DER strictness.
   - fast-check properties: high-S and low-S DER both normalise and recover to the address; parsing random bytes never succeeds silently; JWK and SPKI encodings convert back and forth without loss.
   - CRC32C vectors.
   - The vendored EIP-712 code checked against the package's `verifyTyped`.
2. Unit tests for the signer and adapters:
   - Injected fake SDK clients sign with a local key and return the exact wire formats: AWS SPKI + DER; GCP PEM + DER + CRC (including corrupted CRCs); Azure JWK + r‖s.
   - Assertions on request parameters: `MessageType: DIGEST`, the ARN taken from `GetPublicKey`, `ES256K` with the versioned id, the GCP call options.
   - A fake adapter that returns a signature from the wrong key, and an address-pin mismatch.
   - An AbortSignal timeout, driven by an injected clock. The system timers' cancel is checked with Node's mock timers, so no test waits on the clock for it.
   - The signer's debug lines (`packages/hardhat-kms/test/unit/signer/debug-log.test.ts`): each provider call with its request id and duration, the derived address, the reason for asking for a fresh signature, and the cache's close. A logger reads `DEBUG` when it is created, so the test sets it before it imports the signer modules.
   - The signer cache (`packages/hardhat-kms/test/unit/signer/key-cache.test.ts`): one signer per key, copies of an AWS, Google Cloud or Azure key sharing one signer, a separate signer for keys that differ only in the key id, `profile` (also for an ARN), `region`, `endpoint`, `address`, `timeoutMs`, `displayId`, name, provider, Azure key or vault, and for two configuration variables that hold the same value, one variable name with a different `format` or `default`, or a Google Cloud key whose parts differ in one part's `format`, one signer for copies of a variable with the same `format` and `default`, a variable's `default` absent from the identifier's printed and serialized forms, per-object signers for third-party keys, no identifier read before the provider plugin's error, an unreadable identifier read once by the adapter and again on the next request, a signer created after the last connection closed still closed once by the idle timer, a shared signer kept open until the last connection closes and then closed once, failures not kept, an adapter closed when the signer refuses it, status messages sent to the display it was given, the idle close after the last connection and re-creation on next use, driven by injected timers. `packages/hardhat-kms/test/integration/kms-hook-contract.test.ts` checks that an adapter refused by the contract check is closed too.
   - Bounded GCP CRC retries, and the Azure managed identity timeout.
   - The AWS adapter's tests are in `packages/hardhat-kms-aws/test/unit/adapter.test.ts`, with the fake SDK in `packages/hardhat-kms-aws/test/helpers/fake-aws-kms.ts`.
   - The Azure adapter's tests are in `packages/hardhat-kms-azure/test/unit/adapter.test.ts`, with the fake SDK in `packages/hardhat-kms-azure/test/helpers/fake-key-vault.ts`. They cover `EC` and `EC-HSM` JWKs, coordinates without leading zeros, wrong key types and curves, disabled, expired and not-yet-valid keys, a lookup or sign response whose `kid` names another vault, key or version, a signature of the wrong length, and the errors for 401, 403, 404 and a missing credential. `packages/hardhat-kms-azure/test/unit/credential.test.ts` checks the credential chain's order, the managed identity timeouts, the managed identity left out where it refuses a client id, and the token sharing, with a fake `@azure/identity`. `packages/hardhat-kms-azure/test/integration/managed-identity-exit.test.ts` runs the real chain in a child process with no `az` or `azd` on `PATH` and `AZURE_POD_IDENTITY_AUTHORITY_HOST` pointing at a local endpoint that accepts connections and never answers, and fails unless the process exits on its own within 25 seconds. `packages/hardhat-kms-azure/test/unit/history.test.ts` checks the `kms history` reader against a fake query call, with `KeySign` rows recorded from a real workspace and every id replaced (`packages/hardhat-kms-azure/test/fixtures/log-analytics-rows.ts`). 3. Byte equivalence:
   - A deterministic fake backend (RFC6979 with Hardhat's test key) must produce raw transactions and signatures byte-identical to Hardhat's `local-accounts.ts` vectors: legacy, 2930, 1559, 7702, eth_sign, personal_sign, 712.
   - Differential checks against viem `signTransaction` and ethers `Wallet.signTransaction`.
   - The differential fill test described under [Transaction filling](transactions.md#transaction-filling), run against the Hardhat floor and `latest`. `pnpm run test:hardhat-versions` (`scripts/test-hardhat-versions.ts`) runs two test files, `transaction-filler.test.ts` and `network-hook.test.ts`, on the floor of the `hardhat` peer range and on the newest 3.x release that is at least a day old (or older than `minimumReleaseAge`, if the project sets one). The one-day hold is deliberate: pnpm's built-in default would install a younger release and add it to `minimumReleaseAgeExclude`, which this repository never does, so a younger release is held back and tested by the next weekly run. For each version the script sets the `hardhat` catalog entry in `pnpm-workspace.yaml`, installs, checks that hardhat-kms resolves it, builds, typechecks and runs the tests, then restores `pnpm-workspace.yaml` and the lockfile, also on Ctrl-C. A failure names the Hardhat version and the stage that failed (install, build, typecheck or tests); a failing fill test names the fill step. The `hardhat-versions.yml` workflow runs it weekly, on demand, and on pull requests that change the paths listed in that workflow; it is not a required check.

     No transaction from a fork run reaches Sepolia. Anvil never sends a transaction to its `--fork-url`, and in this suite that URL is a local proxy (`test/live/helpers/rpc-proxy.ts`) in front of the Sepolia RPC, as a second line of defence. The proxy forwards only an allow-list of the reads that anvil's fork backend (`crates/anvil/src/eth/backend/fork.rs` in Foundry) can issue: state, block, transaction, receipt and log reads, `eth_call`, `eth_estimateGas`, `eth_createAccessList`, `eth_simulateV1`, and the `trace_*` and `debug_*` reads that take a hash or a block. Any other method is answered with an error and not forwarded, including `eth_sendRawTransaction`, `eth_callBundle`, `mev_simBundle`, `trace_rawTransaction`, `personal_sendTransaction` and `wallet_sendCalls`. It also refuses a request that holds a hex string of 65 bytes or more, which is the size of a signature, and a body that is not JSON-RPC, including one with a key other than `jsonrpc`, `id`, `method` and `params`, such as `Method`, which Go's case-insensitive JSON decoding would read as the method. A batch with one refused request is refused whole. What it forwards is rebuilt from the parsed request, never the text received, so a duplicate `method` key cannot reach the upstream. The last test of a fork run fails if the proxy refused anything, or if any KMS account's state was not read through it (`eth_getAccountInfo`, `eth_getAccount`, `eth_getBalance` or `eth_getTransactionCount`), which shows the fork the suite sent through is the one behind the proxy. It prints the forwarded methods and how many `evm_mine` nudges the run needed. The proxy also records, for each `eth_feeHistory` it forwards, the upstream's HTTP status and either the JSON-RPC error code or the result's shape (array lengths and value types), and each forward whose upstream fetch failed, by its methods and the error's name and cause code. It keeps no value and no message from an answer, since a message can name the RPC URL. When a provider's fork case fails, the suite prints that record, so a fee read that went wrong upstream shows in the failure ([#395](https://github.com/aelmanaa/hardhat-kms/issues/395)). Anvil ends with the test process: on a normal exit and on SIGINT, SIGTERM or SIGHUP the suite kills it, so it cannot outlive the run with the fork's signed transactions; only a SIGKILL of the test process leaves it running. `close()` sends SIGTERM, then SIGKILL after 5 seconds. A fork run also prints no raw transaction or authorization: both carry Sepolia's chain id and the account's real nonce, so a copy could be broadcast on Sepolia. The suite reports only hashes, and the redaction below removes signed data from failures. A fork run writes no proof, since its hashes exist on no public chain. `test/live/mode.test.ts` checks the mode switch and the anvil lookup, `test/live/rpc-proxy.test.ts` checks the proxy against a fake upstream, and `test/live/anvil.test.ts` kills a parent process holding a stand-in for anvil and checks the stand-in dies too; all three run in `pnpm test`.

     Every receipt must have the status, sender, transaction type and value its case expects. The RPC URL comes from the `HARDHAT_KMS_LIVE_SEPOLIA_RPC_URL` config variable; without it the suite uses `https://ethereum-sepolia-rpc.publicnode.com`, which needs no API key. The legacy and EIP-2930 transactions pay a `gasPrice` of twice the latest base fee or the node's `eth_gasPrice`, whichever is higher, rounded up to a whole gwei, so a rising base fee cannot strand them; the EIP-1559 and EIP-7702 transactions take the plugin's fees. Before anything is sent, each account must hold the run's floor and, on Sepolia, that gas price must be at most 20 gwei; otherwise its test fails and says which limit it hit. The floor comes from the case table: the sum of the `gas` budgets of the cases the mode runs, times that gas price (`balanceFloor` in `test/live/matrix.ts`). On Sepolia, a receipt that does not arrive within 300 seconds fails the test with the transaction's hash and nonce and the account's mined transaction count, so the transaction can be replaced. Public RPCs balance requests across nodes, and a node behind the others can answer a read with state from before the last write. So every read that checks state after a write (`count()`, balances, code, the account's slot 0, the signature checks, and the nonce for the explicit-nonce transactions) asks for the block of the latest receipt. A lagging node then answers "block not found" or "header not found" instead of stale state, and `test/live/helpers/retry.ts` tries the read again, up to 10 times, 2 seconds apart. Waiting for a receipt needs no such pin: viem polls until a node returns the receipt. The cost of a Sepolia run is under [Cost per run](#cost-per-run). Failures go through `test/live/helpers/redact.ts`, which removes each key variable and its parts (the AWS key id split on `:` and `/`, the GCP project, key ring and key, the Azure vault, key and version), the RPC URL, ARNs, aliases, UUIDs, 12-digit account ids, Azure's `key vault '<name>;location=…'` form, GCP project numbers, any URL and any `/v2/` path. It also removes signed data: any hex string of 65 bytes or more, with or without `0x` (raw transactions and signatures), the value of an `r` or `s` field, with or without `0x`, and 32-byte values in an argument list such as viem's `args: (…)` or `recoverPersonal(…)`.    - What runs: StrykerJS 10 with `@stryker-mutator/tap-runner` mutates `packages/hardhat-kms/src/internal/crypto/`, `src/internal/signer/` (not `signer/types.ts`), `src/internal/viem/` (not `viem/types.ts`) and four files of `src/internal/rpc/`: `send-guard.ts`, `dispatcher.ts`, `transaction-filler.ts` and `transactions.ts`. Integration tests are not part of the run.
   - Command: `pnpm run test:mutation`. It is incremental: it reads `packages/hardhat-kms/reports/stryker-incremental.json` and re-tests only the mutants in changed source files and the mutants covered by changed test files. A change outside those files is not seen: a dependency update, or a change to unmutated source that the mutated code imports, such as `errors.ts`, `error-catalog.ts`, `rpc/chain-id.ts` or `rpc/typed-data.ts`. Such a change shows only in a full run; `pnpm --filter hardhat-kms exec stryker run --force` tests every mutant. The HTML report is `packages/hardhat-kms/reports/mutation/mutation.html`; the clear-text output lists each surviving mutant with its diff, then a score table per file. `reports/` and `.stryker-tmp/` are gitignored.
   - Three settings in the config need a reason, which sits next to each as a `_comment` key. `tsconfigFile` names a file that does not exist: Stryker rewrites `tsconfig.json` in its sandbox with the `typescript` package's `parseConfigFileTextToJson`, which TypeScript 7 does not export, so the run fails. The rewrite only serves Stryker's TypeScript checker, which this setup does not use. `plugins` names the tap runner: Stryker's default plugin glob only searches the folder next to its own install, where pnpm does not put the runner. An exclusion (`!`) goes to every shard of its directory, and a directory shard leaves out the files that have shards of their own, so no mutant is tested twice. A file entry with other characters in its name than lowercase letters, digits and `-` runs in its directory's shard. An entry outside `src/internal/<directory>/` fails the plan, so a new entry cannot fall outside every shard. Each shard checks its own score against `break`, and a `score` job adds up the shards' JSON reports and checks the total. Everything below applies per shard. GitHub evicts cache entries unused for 7 days, so most weekly runs find no incremental file and test every mutant. On the 1st of each month, and when dispatched with `force`, it tests every mutant, and its results replace the incremental ones. When the 1st is a Monday, the weekly run skips itself and only the monthly full run tests. The workflow passes `--concurrency 2`, since the score depends on the worker count (below). Each shard uploads its HTML and JSON report as the `mutation-report-<shard>` artifact, kept 14 days, and writes its score table to the job summary. Each shard job has a 120-minute limit, well above the slowest shard's expected time, since a shard cancelled at its limit saves no incremental file and would start from scratch the next week. It is not a required check and has no `pull_request` trigger, so the gate runs after merge: a pull request that leaves survivors does not fail its own checks, it turns the next weekly run red.    - Threshold: `thresholds.break` in the config. A score below it exits 1 and fails the scheduled run; the run's incremental file is still saved, marked `fail`, so the next night does not skip. It starts at the baseline rounded down, minus a margin that absorbs timeouts that depend on the machine: `floor(score) − max(2, ceil(100 × timeouts / valid mutants))`, where valid mutants exclude the ignored ones and the runtime errors. The margin is 2 points unless timeouts make up more than 2% of the mutants. To raise it, a pull request that raises the score sets `break` the same way from the new CI score. Lowering it needs a reason in the pull request.
   - Equivalent mutants: a mutant that behaves like the original for every input the code can receive cannot be killed. An injectable seam, such as `Timers` or an adapter, counts as an input within its contract (a `Timers` never runs a callback inside `setTimeout`, as real timers never do): a guard that only a misbehaving seam can reach, such as a `Timers` whose cancel does nothing, is tested with such a seam, not marked. An equivalent mutant is marked in the source with `// Stryker disable next-line <Mutator>: <reason>`, and the reason says why the edit changes nothing, so a reader can check it, as for type escapes. Stryker reports the mutant as ignored, outside the score. The comment applies to every mutant of that mutator whose node starts on the next line. Babel places a `&&` or `||` expression at its first operand, so a redundant operand goes last, on its own line, with the comment above it: placed first, the comment would also skip the mutants of the whole condition, such as the one that turns a key comparison into `true`. Where the equivalent mutant and a killed one are on the same node, for example `n < 256` changed to `n <= 256` or to `n >= 256`, the comment skips both, and the pull request lists the killed ones. An unreachable block is marked with `// Stryker disable BlockStatement: <reason>` before the `if` and `// Stryker restore BlockStatement` after it, since its opening brace shares a line with the end of the condition. An `else` block cannot take a line comment of its own, since a comment before `else` belongs to the block above it; `signer-identity.ts` puts the directive in a block comment between `else` and its brace. Test code follows a few conventions:

- Each test opens a fresh connection with `hre.network.create()` (`connect()` is deprecated since Hardhat 3.18; `getOrCreate()` reuses cached connections, so per-connection state must tolerate reuse).
- HRE test files run with `concurrency:false`.
- Test globs are quoted in scripts, so the shell does not expand them.
- Helpers live in each package's own `test/helpers`, because `hardhat-test-utils` is private.
- The root `test`, `test:unit` and `coverage` scripts run `pnpm run build` first, because provider packages import the core from its built `dist/`.
- Code that removes a directory with `rmSync(..., { recursive: true })` stays out of the real temp directory, and so do its tests. A mutant that replaces the per-run directory with `tmpdir()` would make the test remove the real temp directory. `scripts/pack.ts` and `test/scripts/pack.test.ts` are the model:
  - The code checks the path first and refuses anything outside the directories it created. `removePackDirectory` removes only a `hardhat-kms-pack-*` directory directly under `os.tmpdir()`.
  - A test of such code runs it under a temp directory the test creates. In `before` it sets `TMPDIR`, `TEMP` and `TMP` to that directory and asserts that `os.tmpdir()` returns it; in `after` it restores the three variables and removes the directory. `TEMP` and `TMP` are for Windows, where `os.tmpdir()` reads `TEMP`, then `TMP`, and ignores `TMPDIR`.
  - A mutant you make by hand in such code (Stryker does not cover `scripts/`) runs under the same sandbox: set the three variables in the shell before `node --test`, for example `TMPDIR=$sandbox TEMP=$sandbox TMP=$sandbox node --test test/scripts/pack.test.ts`.

Coverage uses c8 on native TypeScript (Node 24), with a threshold of 95% for lines, branches, functions and statements across each package's `src/`, set in the package's `.c8rc.json`. Provider adapters are tested with fake SDK clients, so they are held to the same bar. `types.ts` and `type-extensions.ts` are excluded.

Deprecated APIs are checked in four places. `pnpm run check` lints our own code with `typescript/no-deprecated`. `pnpm run docs:check` lints the TypeScript snippets of the docs and READMEs with the same rule. `pnpm run pkg:check` fails on a deprecated package in a published package's production tree, and the Node 26.0.0 leg of the CI test job fails any Node process of the tests, Hardhat CLI runs included, that emits a `DeprecationWarning` not on its allowlist; worker threads are not covered (see [Tooling](tooling.md)). A test that calls a deprecated API on purpose fails that leg. Set `process.noDeprecation` around that one call, as the providers' `test/helpers/import-recorder.mjs` do for the `module.register` fallback that Node 22.13 needs, or, for a warning a dependency emits, add its code to `ALLOWED_WARNINGS` in `scripts/deprecation-hook.ts` with the reason and the upstream link. Each check has its tests in `test/scripts/`, with fixtures in `test/scripts/fixtures/`.

## Test time limits

The `test:unit` and `test:integration` scripts of the four packages run `node --test` through `scripts/node-test.ts`, which chooses the `--test-timeout` value by Node major. The flag means two different things:

- On Node 24 and later it limits each test. A file may run as long as its tests need.
- On Node 22 it limits each test file and sets no limit per test. The runner ends a file that runs past the value with SIGTERM, even when every test in it passes.

Node changed the flag in [nodejs/node#57672](https://github.com/nodejs/node/pull/57672), first released in 24.0.0. The 22.x line does not have the change.

| Script             | Node 24 and later: limit per test | Node 22: budget per file |
| ------------------ | --------------------------------- | ------------------------ |
| `test:unit`        | 30 s                              | 300 s                    |
| `test:integration` | 120 s                             | 600 s                    |

The file budget is sized to end a hung file, not to time a test: a file such as `tasks-cli.test.ts` starts the Hardhat CLI 37 times across its 33 tests and, on a loaded machine, can run for minutes with every test passing. So on Node 22 a hung test is reported as a cancelled file after up to 10 minutes (5 for a unit file), not as a failed test. The same tests run on Node 24 and 26, where the runner cancels the hung test by name at its limit. A test's own `timeout` option and the limits of the CLI helper apply on every version. In CI the job's 15-minute timeout stays the outer limit.

The localstack, examples and live scripts pass one `--test-timeout` value on every version, and `coverage` passes none. CI runs the localstack, examples and coverage jobs on Node 24, and `live-tests.yml` runs `test:live` on Node 24; the live scripts also run locally, and on Node 22 their value limits each file. `test/scripts/node-test.test.ts` runs fixture files through the script with limits of a few seconds: a file whose passing tests together run longer than the per-test limit passes on every version, a slow test is cancelled at the per-test limit on Node 24 and later, and on Node 22 its file is cancelled at the budget.

When the Node floor moves to a release that has the change (24.0.0, or a later 22.x release if the 22.x line ever gets it), delete the file budgets and the script, and put `--test-timeout` back in the package scripts.

## Run the tests on the published floor

The published packages' Node.js floor is `engines.node` in `packages/*/package.json` ([Support](../user/reference/support.md)). Developing in the clone needs Node >= 22.18.0 (root `devEngines`), because the scripts and hooks run `.ts` files with plain `node`, and 22.18.0 is the first 22.x release that strips types without a flag. So on the published floor, `pnpm test` stops with `ERR_PNPM_BAD_RUNTIME_VERSION` before it runs anything. To run the suite there anyway, for example to reproduce a failure of the CI `Test (Linux, Node 22.13.0)` job, set two variables:

```sh
nvm install 22.13.0   # installs it if needed and switches to it
pnpm_config_runtime_on_fail=ignore NODE_OPTIONS='--import tsx' pnpm test
nvm use               # back to the Node in .nvmrc
```

- `pnpm_config_runtime_on_fail=ignore` stops pnpm from refusing the runtime. pnpm checks `devEngines.runtime` on `pnpm run` and `pnpm exec` too, not only on `pnpm install` ([`runtimeOnFail`](https://pnpm.io/settings/cli#runtimeonfail)). It has to be the environment variable: the root scripts call `pnpm run` and `pnpm -r run` again, and the `--runtime-on-fail=ignore` flag does not reach those nested calls, while every child process inherits the variable.
- `NODE_OPTIONS='--import tsx'` preloads [tsx](https://tsx.is), a devDependency, into every Node process, so the `.ts` scripts and test files load on a Node that does not strip types. Without it the first script fails with `ERR_UNKNOWN_FILE_EXTENSION`.

The CI 22.13.0 legs of `.github/workflows/ci.yml` and `ci-all-os.yml` run `pnpm test` with the same two settings. `pnpm_config_runtime_on_fail=warn` works too: it runs the suite and prints a `[WARN]` line at each pnpm call. Set either one for this run only; the development floor stays at 22.18.0.

## Live transaction matrix

The live suite's coverage is a table in `test/live/matrix.ts`: every action (a transfer, a deploy, a call, a revert, a replacement, an EIP-7702 delegation and so on) against every transaction type from 0 to 4, plus `personal_sign`, `eth_signTypedData_v4` and `eth_sign`. Each cell has exactly one decision, and the same decision applies to each configured provider. A cell that one provider could not run would need its own decision and reason. `pnpm run docs:live-proof` renders [Live proof](../live-proof.md) from a Sepolia run: the table with the decision of each cell, then a transaction hash for each live cell and provider.

`test/live/matrix.test.ts` runs in `pnpm test`, with no keys and no network. It fails when:

- a cell has no decision, more than one, or a decision for a cell that does not exist;
- a `live` or `fork` decision names a case that does not cover the cell, a case covers a cell whose decision does not name it, a case runs in another mode than its decision, or a case sends another type than its cells;
- a `fork`, `refused` or `n/a` decision has no reason, or a reason that does not fit it: reasons (a), (d), (e) and (h) say why a cell cannot run on Sepolia and may only make it `fork`, (b), (c), (f) and (g) say why the protocol forbids it and may only make it `n/a`, and (r) only `refused`;
- a `unit` or `refused` decision, or the unit test a `fork` decision also names, points to a file that does not exist or that has no `it(` or `test(` call with that literal title. A title in a comment, in `it.skip(` or `it.todo(`, or in a call with a `skip` or `todo` option does not count.

It also tests the per-run check, the balance floor and the renderer on made-up runs. It also checks the committed proof: `test/live/proof.json` must be for Sepolia, list AWS, Google Cloud and Azure once each, and have a transaction hash for every live cell of each, and `docs/live-proof.md` must be the page rendered from it. Only a Sepolia run with all three providers configured, all passing, writes the file, so a run with fewer cannot overwrite a complete proof. The two checks are skipped only while the file is missing and `docs/live-proof.md` is still the hand-written page from before the matrix. The rendered page says it is rendered from `test/live/proof.json`, so once it is committed, a missing proof fails.

### Decisions

| Decision  | Meaning                                                                                                                                   |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `live`    | A case runs it on Sepolia and in fork mode.                                                                                               |
| `fork`    | A case runs it only in fork mode. The reason says why it cannot run on Sepolia.                                                           |
| `unit`    | Only a unit or integration test covers it. The decision names the file and the test.                                                      |
| `refused` | The plugin refuses it before any request, and a unit test checks the refusal. Blob transactions (type 3) are refused.                     |
| `n/a`     | The protocol does not allow it. The reason quotes the EIP, for example the null destination that EIP-4844 and EIP-7702 forbid in deploys. |

The fork-only cases are the self-sends of types 0 and 1, the reverts of types 0, 1 and 4, the replacements of types 0, 1, 2 and 4, and a local account that sends the KMS key's authorization. A replacement turns automine off with `evm_setAutomine`, sends a 1 wei self-send, sends a second one with the same nonce and double the fees, mines one block, and checks that only the second was mined. Automine is a setting of the whole node, so a replacement case holds a lock that no other provider's case holds at the same time (`test/live/helpers/lock.ts`). The local sender is a key generated in memory and funded with `anvil_setBalance`; the KMS key signs its authorization with the account's current nonce, since another account sends it. The reverting type 4 case delegates the account back to `LiveCheck` from the 3-byte contract and checks the delegation stays applied, since EIP-7702 does not roll back processed authorizations when execution fails.

### Cost per run

A Sepolia run sends 15 transactions per provider. In a fork run on 2026-10-02 the live cases used 1,133,870 gas per provider, of which `LiveCheck`'s deploy is about 667,000. That is about 0.0011 ETH per provider at 1 gwei, and about 0.0034 ETH for the three providers. The legacy and EIP-2930 transactions pay at least twice the base fee, so a run costs more than the 1 gwei figure. The fork-only cases cost nothing.

### Add a case

1. Add the case's id to `CASE_IDS` and its entry to `CASES` in `test/live/matrix.ts`, in the place it should run: its mode, its type, the cells it covers, the status and sender its receipts must have, a `gas` budget above what its transactions use together, and a title for the docs.
2. Point each cell it covers at it in `DECISIONS`, with a reason from `REASONS` for a `fork` decision.
3. Add its step to `STEPS` in `test/live/cases.ts`. The typecheck fails until every case has one. Send through `ProviderRun.mined`, which checks the receipt against the case and records it.
4. Run `pnpm test` for the completeness check, then `pnpm run test:live` in fork mode with every provider.
5. A new live case changes the proof: run the suite on Sepolia, then `pnpm run docs:live-proof`, and commit `test/live/proof.json` with `docs/live-proof.md`.

## Live tests in GitHub Actions

`.github/workflows/live-tests.yml` runs `pnpm run test:live` on a GitHub-hosted runner with the AWS, Google Cloud and Azure test keys. The job signs in to the three clouds over OIDC, so the repository holds no cloud credential: no access key, no `AZURE_CLIENT_SECRET`, no service account key.

### Triggers

- Manual dispatch, from the Actions tab or with `gh workflow run live-tests.yml -f network=fork`. The `network` input is `fork` (the default: a local anvil fork of Sepolia, which spends nothing) or `sepolia` (spends Sepolia ETH and writes `test/live/proof.json`).
- The label `ci:live` on a pull request whose branch is in this repository. Adding it runs that pull request's code, always in fork mode. A later push does not run the tests again: remove the label and add it again, which asks for a new approval of the new code. Any other label starts nothing.
- On a pull request from a fork, the label runs nothing: GitHub gives such a run no OIDC token and no environment secrets, so a small job writes a notice in the run's summary instead. To test it, a maintainer pushes the reviewed commits to a branch of this repository and dispatches the workflow on that branch.

There is no schedule, and no `push`, plain `pull_request` or `pull_request_target` run.

### Who approves

The job runs in the `live-tests` environment, whose required reviewer is the owner. Every run, dispatched or labelled, waits for that approval before it starts. An approved run executes the code of its branch with the right to sign with the three test keys, so before approving a label run, read the pull request's diff, including any change to the workflow itself, to the test helpers and to the dependencies. A dependency update changes code the diff does not show, since its diff is mostly the lockfile. Then check the run itself:

- Its commit, on the run page, must be the pull request head you read. A run is pinned to the commit it was started on: if the branch moved after that, the page shows code the run will not execute. Reject such a run, then remove the label and add it again.
- It must be a `Live tests` run that you started, with the label or a dispatch. Any workflow on any branch that names `environment: live-tests` asks for the same approval; reject every other request.

Agents never dispatch the workflow, never add `ci:live` and never approve the environment.

### Trust

Only the `live` job has `id-token: write`; the workflow's default is `permissions: {}`. Each cloud trusts one token subject, the immutable form that names the environment: `repo:aelmanaa@<owner id>/hardhat-kms@<repository id>:environment:live-tests`.

| Cloud        | Trusted identity                                                                        | What it may do                                    |
| ------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------- |
| AWS          | An IAM role whose trust policy checks the audience `sts.amazonaws.com` and that subject | `kms:Sign` and `kms:GetPublicKey` on the test key |
| Google Cloud | The subject itself, as a principal of a workload identity pool, with no service account | Sign with the test key and read its public key    |
| Azure        | A user-assigned managed identity with a federated credential for that subject           | Read the test key and sign with it                |

A run outside the environment gets a token with another subject, which the three clouds refuse. This holds even when a pull request removes `environment: live-tests` from the workflow: its run then needs no approval, but it gets no credentials either. The three test keys hold only Sepolia ETH. The `azure/login` step prints the token's subject in the public log; both ids in it are public (`gh api repos/aelmanaa/hardhat-kms` shows them) and the subject grants nothing by itself.

The `live-tests` environment stores identifiers, not credentials. Its secrets are `LIVE_AWS_ROLE_ARN`, `LIVE_GCP_WORKLOAD_IDENTITY_PROVIDER`, `LIVE_AZURE_CLIENT_ID`, `LIVE_AZURE_TENANT_ID` and the three key variables the suite reads (`HARDHAT_KMS_LIVE_AWS_KEY_ID`, `HARDHAT_KMS_LIVE_GCP_KEY`, `HARDHAT_KMS_LIVE_AZURE_KEY_ID`); its variable `LIVE_AWS_REGION` gives the AWS region. A `HARDHAT_KMS_LIVE_SEPOLIA_RPC_URL` secret is optional; without it the suite uses its public RPC. The key variables reach only the step that checks they are set, the balance check and the test step, and the suite's redaction removes them from every failure.

### What a run does

1. Checks out the branch, installs with `pnpm install --frozen-lockfile --ignore-scripts` and builds, with no dependency cache.
2. In fork mode, installs anvil from Foundry v1.8.1 with `foundry-rs/foundry-toolchain`.
3. Builds `test/live/fixture-project`, which downloads Solidity 0.8.24 into Hardhat's compiler cache; the suite's own build then finds it there. Steps 1 to 3 are everything the run installs or downloads, and all of it happens before the first cloud login, so no install script and no download runs with credentials.
4. Fails unless the three key variables are set. The suite skips a provider whose key is empty and still passes, so without this check a missing secret would give a green run that tested fewer providers.
5. Signs in with `aws-actions/configure-aws-credentials`, `google-github-actions/auth` and `azure/login` (with `allow-no-subscriptions`, since the identity has a role on one key and none on a subscription).
6. In Sepolia mode, checks the balances before anything is sent: each of the three accounts must hold the run's floor (`balanceFloor` in `test/live/matrix.ts`) at the suite's legacy gas price, and that price must be at most 20 gwei. Otherwise the run fails, naming the provider, the address and how much ETH is missing. The suite checks each account again, but its providers run in parallel, so without this check two of them could spend ETH on a run that cannot write a proof.
7. Runs `pnpm run test:live`.
8. In Sepolia mode, after a passing run, uploads `test/live/proof.json` as the `live-proof` artifact, kept 7 days. The workflow never commits it: download it to `test/live/proof.json`, run `pnpm run docs:live-proof` and commit both files in a pull request.

### Time, concurrency and cost

- The job's limit is 30 minutes in fork mode and 45 on Sepolia, counted from when the job starts, after the approval.
- One live run at a time across the repository (concurrency group `live-tests`; a running job is never cancelled), so two Sepolia runs never race on the accounts' nonces. GitHub keeps one more run pending in the group; a newer run replaces a pending one, never the one that runs.
- Standard GitHub-hosted runners are free for public repositories. A fork run spends no ETH; a Sepolia run spends about 0.0034 ETH at 1 gwei, and up to about twenty times that at the 20 gwei cap (see [Cost per run](#cost-per-run)). Each run makes a few dozen signing calls per key: AWS KMS charges about $0.15 per 10,000 of them, so a run costs well under a cent there. The Google Cloud HSM and Azure prices per operation were not checked.
