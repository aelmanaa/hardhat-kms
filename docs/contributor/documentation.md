# Documentation

Audience: Anyone writing or reviewing hardhat-kms docs.

Status: The structure and rules apply now. The pages under [Planned pages](#planned-pages) arrive with their issues.

User docs follow the Diátaxis split: each page is a tutorial, a how-to guide, reference or explanation, and does only that job. Contributor docs and decision records live in a separate tree.

| Kind        | Answers                       | Where                         |
| ----------- | ----------------------------- | ----------------------------- |
| Tutorial    | "Show me, start to finish."   | `docs/user/tutorials/`        |
| How-to      | "How do I do this one thing?" | `docs/user/guides/`           |
| Reference   | "What exactly does X accept?" | `docs/user/reference/`        |
| Explanation | "Why does it work this way?"  | `docs/user/explanation/`      |
| Contributor | "How is the code built?"      | `docs/contributor/`           |
| Decision    | "Why was it done this way?"   | `docs/contributor/decisions/` |

## Rules

- Docs ship with the code. A feature's issue lists the pages it adds or changes, and its pull request includes them.
- Every page under `docs/user/` starts with YAML frontmatter holding a `title` and a one-sentence `description`, written for the question the page answers; the docs site uses them for the HTML title, the meta description and the search index. [Checks](#checks) has the exact rules.
- Every page states its audience. A user page says what works and what was checked, in terms a reader outside the project understands: no milestone codes, no notes for maintainers in HTML comments, and no issue links unless a reader benefits, such as one that tracks a known limitation. History goes to the changelog. Links to contributor docs from a user page are marked as optional. `pnpm run docs:check` enforces the first two.
- Every page is linked from [docs/README.md](../README.md) and from [AGENTS.md](../../AGENTS.md). Decision records are linked from the [decision index](decisions/README.md) instead of docs/README.md.
- Every exported symbol has TSDoc, enforced by lint.
- The provider tutorials share one shape. [First deploy on Sepolia with AWS KMS](../user/tutorials/first-deploy-aws.md) is the template for the [Google Cloud KMS](../user/tutorials/first-deploy-gcp.md) and [Azure Key Vault](../user/tutorials/first-deploy-azure.md) tutorials:
  - Shared, copy as is: step 1, step 5, steps 6 and 7, the return-funds half of step 8, Next steps. In the shared parts, change only the provider's name and key terms (key or key version, Sign or AsymmetricSign) in: the audience and intro lines, step 5's second paragraph, step 6's sentence on the Sign call, step 7's last sentence and step 8's opening sentence.
  - Kept out of the tutorials, and linked instead: the fork rehearsal and the explorer troubleshooting live in [Deploy with Hardhat Ignition](../user/guides/deploy-with-ignition.md), and the return-funds script in [Return the funds from a KMS address](../user/guides/return-funds.md). A tutorial step holds the main path; an optional or failure-only detour goes to a guide and gets one sentence and a link.
  - Provider-specific, rewrite per provider: the region and credentials prerequisites, the cost paragraph, steps 2 and 3, the install line and the `kms.keys` entry in step 4, the key removal in step 8.
- Each tutorial's line under the audience says when and at which commit the tutorial was last followed from an empty directory. It is how a reader judges freshness, so whoever follows the tutorial in a live run updates its date, commit and versions in the same pull request.
- Examples use the real API and must run. The live tests run each tutorial's steps on Sepolia. `packages/hardhat-kms/test/integration/tutorial-return-funds.test.ts` reads `scripts/return-funds.ts` from the [return-funds guide](../user/guides/return-funds.md), checks that the tutorials link it and carry no copy, and runs it against a local `hardhat node`.
- Never put credentials, real key ids or API-keyed RPC URLs in docs. Use placeholders such as `alias/deployer` and `configVariable("SEPOLIA_RPC_URL")`.

## Checks

`pnpm run docs:check` runs `scripts/check-docs.ts`, locally and in the CI Docs job. It checks ten things:

- Every TypeScript snippet (` ```ts `, ` ```typescript ` or a `~~~` fence) in `README.md`, each `packages/*/README.md` and `docs/`, apart from the generated API pages, typechecks as its own program, with strict settings, against the built packages: `hardhat-kms`, `@hardhat-kms/aws`, `@hardhat-kms/azure` and `@hardhat-kms/gcp` resolve from the root's dependencies through each package's `exports`, as they do in a user's project, so a missing export fails the check. The root also lists `@nomicfoundation/hardhat-ignition` and `@nomicfoundation/hardhat-ignition-viem` as development dependencies, only for the snippets of the [Ignition guide](../user/guides/deploy-with-ignition.md), and `@nomicfoundation/hardhat-toolbox-viem`, only for the tutorials' configs, which start from Hardhat's viem template; knip ignores them. Errors point at the Markdown file and line; a compiler failure without errors fails the check too. After the typecheck, one oxlint run with only `typescript/no-deprecated` lints the same snippet programs, so a snippet that calls an API marked `@deprecated`, such as Hardhat's `network.connect()`, fails with its file and line. A snippet that typechecks and default-exports `defineConfig(...)` is then loaded the way `npx hardhat` loads `hardhat.config.ts`: `scripts/load-config-snippets.ts` imports it with Hardhat's `importUserConfig` and passes it to `createHardhatRuntimeEnvironment`, which runs every plugin's config validation, so a config that typechecks and still fails in Hardhat, such as an `address` pin of `"0x…"`, fails with the line of its opening fence and Hardhat's message. All configs load in one child process, which writes its results to a file, so a config that prints while it loads cannot hide them. Its environment has no `HARDHAT_` variables, which would set global options such as `--kms`, and gives every `configVariable` the snippets name a placeholder value. Hardhat resolves configuration variables only when a value is used, and no task runs, so nothing connects to a network or calls a KMS. Only a snippet that contains `export default defineConfig(` is loaded. A key whose provider package is missing from `plugins` still passes, because the plugin reports that when the key is first used. `scripts/doc-snippets.ts` holds the snippet checks and `test/scripts/doc-snippets.test.ts` their tests. To exclude a snippet that is not meant to compile, such as a sketch of a planned API, put `<!-- docs-check: skip -->` on its own line before it. The fences of a VitePress `::: code-group` block, which the site shows as tabs, are ordinary fences with a label after the language (` ```ts [AWS KMS] `), so each tab is checked as its own snippet; GitHub shows the `:::` lines as plain text, so keep them on their own lines with a blank line on each side.
- Every page under `docs/` is linked as the [rules](#rules) require. Decision records need the `AGENTS.md` link and a line in the decision index instead of `docs/README.md`; the decision template is exempt. The generated API pages need a link from their own index, `docs/user/reference/api/README.md`, which the two indexes link. Only real links count, not paths in code or HTML comments.
- The [errors reference](../user/reference/errors.md) matches the error catalogues. `scripts/generate-errors-doc.ts` imports each listed package's `src/internal/error-catalog.ts`, which Node runs as TypeScript, so no build is needed; the check renders the page again in memory and fails if the file differs. Run `pnpm run docs:errors` after changing a catalogue entry. The packages are listed in `CATALOGUED_PACKAGES`; a package under `packages/` that the script does not list fails the check, and so does a listed package without its catalogue.
- The [API reference](../user/reference/api/README.md) matches the TSDoc of the built packages. `scripts/generate-api-docs.ts` runs TypeDoc from `tools/api-docs` ([decision 0012](decisions/0012-api-reference-generator.md)) on the built `.d.ts` file of each export of `hardhat-kms`, listed from its `package.json`, and formats the pages with oxfmt; the check renders them again in a temporary directory and fails on a page that is missing, extra or different. TypeDoc treats its warnings as errors, such as a public type that refers to a type that is not exported, or a `{@link}` to something not documented. The pages have no "Defined in" links, which would print build paths. Run `pnpm run docs:api` after changing a TSDoc comment or a public type. The script runs `tsc -b` on the packages first, so the pages never come from a stale `dist/`, and runs TypeDoc in the C locale, so the anchors are the same under any system locale. The provider packages export only their plugin, so they have no page; the check fails if one exports anything else.
- First-party source builds its errors only through the catalogue helpers (`catalogError`, `catalogMessage`, `internalError`). The check parses each file with oxc-parser, so comments, strings and regular expressions cannot hide or fake a match, and fails, with the file and line, on: `kmsError` named anywhere outside its definition and export (a call, an import or an alias); `new HardhatPluginError(`; a `new` or a call of a class whose name, or last segment as in `ns.FooError`, ends in `Error`, `Failure` or `Exception`, without `catalogMessage` in its arguments; `new this.#x(…)` or `new obj.X(…)` with text in its arguments and no `catalogMessage`; and a thrown string. `src/internal/vendor/` is skipped.
- The pages a user reads, `docs/user/`, `README.md` and each `packages/*/README.md`, hold no HTML comment other than `<!-- docs-check: skip -->`. Code (fenced, indented or inline) does not count. Notes for maintainers go on a contributor page such as this one. Milestone codes such as `M5` are refused on these pages too, with the same rule as the next check; put a name that only looks like one in backticks. `scripts/user-pages.ts` holds both rules and `test/scripts/user-pages.test.ts` their tests.
- No tracked file that ships, is generated or is read on GitHub names an internal milestone, a review round or the maintainer's machine: no milestone code such as `M5` outside code (Apple chip names such as `M1` are allowed), none of the words `owner decided`, `review found`, `in review`, `after review` or `fresh-reader`, and no `Darwin`, `os/macos` (the AWS user-agent token; the `macOS` runner name may stay), `/Users/`, `/private/tmp` or `/home/`. The rule: a code comment, docs page, changeset or generated page says what exists and what was checked, never which milestone, decision or review round produced it, and never the machine, accounts or keys it was made on. The check reads `git ls-files` under `packages/*/src`, `packages/*/test`, `test`, `scripts`, `examples`, `.changeset`, `.github`, `docs` (the generated API pages and `docs/live-proof.md` included), `README.md`, `packages/*/README.md`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `SECURITY.md`, `skills` and `context7.json`. A Markdown file is checked as prose, with code, URLs and link targets blanked; an SVG file with its drawing data (`d`, `points`, `viewBox`, `transform`) blanked, since a path command such as `M40 0` looks like a milestone code; a binary image (PNG, JPEG, GIF, WebP, ICO) is skipped; any other file is checked whole, so a fixture's user agent counts. `scripts/user-pages.ts`, `scripts/check-docs.ts` and `test/scripts/user-pages.test.ts` are exempt, since they hold the patterns and their test data. A recorded fixture keeps the shape of what the SDK emits with every version token zeroed and the OS as Linux, as `hardhat-kms/0.0.0` is; a test's sample address is visibly synthetic (`0x1111111111111111111111111111111111111111`) or a documented test vector such as Hardhat's first default account, never a live key's.
- Every ` ```mermaid ` block in `README.md`, each `packages/*/README.md` and `docs/` parses with `mermaid.parse()` from the `mermaid` package, which runs in Node without a browser. Flowchart and state diagram labels go through DOMPurify, which needs a DOM to sanitise; parsing needs only the syntax, so `scripts/mermaid-blocks.ts` gives the copy of DOMPurify that Mermaid imports a no-op `addHook` and `sanitize` before it loads Mermaid. The root lists `dompurify` at the version Mermaid resolves, so the two share one copy; update both together. A block that does not parse fails the check with its opening fence's line and Mermaid's message. The line number inside Mermaid's message is not the file's: Mermaid adds lines to a flowchart before it parses it. `test/scripts/mermaid-blocks.test.ts` holds the tests, with broken flowcharts and sequence diagrams and a node named `call`, a Mermaid keyword that breaks the diagram. GitHub renders with its own copy of Mermaid, which can lag the one in the lockfile, so check a new diagram type on a pull request's rendered page too.
- Every page under `docs/user/`, the generated ones included, has frontmatter: a `title` of at most 60 characters equal to the page's H1 (the first `# ` heading outside a fence), and a one-line `description` of 40 to 160 characters that no other page has. A missing block, invalid YAML, a missing or empty field, a title that differs from the H1, a description out of range or on several lines, and a duplicate description each fail with the file. The two generators write the frontmatter of the pages they own: `scripts/generate-api-docs.ts` from its `API_DESCRIPTIONS`, `scripts/generate-errors-doc.ts` from `ERRORS_DOC_FRONTMATTER`. On GitHub the frontmatter shows as a small table above the H1. `scripts/frontmatter.ts` holds the rule and `test/scripts/frontmatter.test.ts` its tests.
- The agent skill, [skills/hardhat-kms/SKILL.md](../../skills/hardhat-kms/SKILL.md), is checked like a user page: its snippets typecheck, it holds no HTML comment or milestone code, its Mermaid blocks parse and it names nothing internal. Its frontmatter has a `name` equal to its directory and a `description` of at most 1024 characters, the Agent Skills limits. `npx skills add` copies the skill without the repository, so it links to the docs by their `https://github.com/aelmanaa/hardhat-kms/blob/main/` URLs, and the check fails on such a link whose file does not exist. `scripts/skills.ts` holds these two rules and `test/scripts/skills.test.ts` their tests. The full format check, run by hand when the skill changes, is `skills-ref validate skills/hardhat-kms` from the [skills-ref](https://github.com/agentskills/agentskills/tree/main/skills-ref) Python package; its PyPI release names the command `agentskills`.

[lychee](https://lychee.cli.rs) checks links, configured by `lychee.toml`. On every pull request the CI Docs job checks internal links and `#anchors` offline. A weekly workflow, `.github/workflows/docs-links.yml`, also checks external links, so a website that is briefly down cannot block a merge. To run the pull request check locally from the repository root:

```sh
docker run --rm -v "$PWD:/repo" -w /repo lycheeverse/lychee:0.24.2 --offline --config lychee.toml README.md AGENTS.md CLAUDE.md CONTRIBUTING.md SECURITY.md packages/hardhat-kms/THIRD_PARTY_NOTICES.md .github/pull_request_template.md 'packages/*/README.md' 'examples/README.md' 'examples/*/README.md' 'docs/**/*.md' 'skills/**/*.md'
```

## The docs site

The pages under `docs/` are also published as a site, at <https://aelmanaa.github.io/hardhat-kms/> ([decision 0017](decisions/0017-docs-hostname.md)). The Markdown stays the source: write a page for GitHub, with relative links to `.md` files, and the site renders it as it is. `tools/docs-site` is a private package, never published, that builds the site with VitePress; `.vitepress/config.ts` holds the settings and `.vitepress/site.ts` the hostname, base path and helpers that `scripts/check-site.ts` shares.

What the site contains and how it maps the Markdown:

- `docs/user/`, `docs/live-proof.md` and `docs/README.md`, which becomes the landing page: the config adds the hero and three feature cards above it, so the file needs no frontmatter. A folder's `README.md` is served as its index, so `user/reference/api/README.md` is at `/user/reference/api/`.
- Contributor pages stay on GitHub. A link that leaves the site, to `docs/contributor/`, `CONTRIBUTING.md`, `SECURITY.md` or an example project, is rewritten to the file on GitHub's `main` branch, in the HTML pages, the `.md` copies and `llms-full.txt`.
- The generated pages, the [errors reference](../user/reference/errors.md) and the [API reference](../user/reference/api/README.md), have no edit link: a change goes into the error catalogues or the TSDoc, as [Checks](#checks) describes.
- Headings get the anchors GitHub gives them, such as `#hardhat-kmsgcp` for `@hardhat-kms/gcp`, so a `#fragment` that works on GitHub works on the site.
- ` ```mermaid ` blocks are drawn in the browser by the `mermaid` package, the same version `docs:check` parses them with, in the light or dark scheme the reader picks.
- The sidebar follows the order of [docs/README.md](../README.md), grouped by folder; a page added to the index appears in the sidebar too.

For search engines and agents:

- URLs have no `.html` (`cleanUrls`). Every page has one `canonical` URL, `og:url`, `og:title`, `og:description`, the social preview's tags and a Twitter card. The title is the page's H1, or its frontmatter `title`, followed by `| hardhat-kms`; the meta description is the frontmatter `description`, or the site's description when the page has none.
- The social preview is `docs/public/og-image.png`, a 1280x640 PNG drawn from `docs/public/og-image.svg`. VitePress copies `docs/public/` to the site root as it is, so the image is served at `https://aelmanaa.github.io/hardhat-kms/og-image.png`. `og:image` and `twitter:image` give that absolute URL, with `og:image:width`, `og:image:height` and the alt text in `og:image:alt` and `twitter:image:alt`; `site.ts` holds the URL, size and alt text.
- To change the social preview, edit the SVG, run `pnpm run docs:og` and commit both files. The script (`scripts/render-og-image.ts`) renders the SVG with `@resvg/resvg-js` from the fonts in `tools/docs-site/fonts/` only, never from the machine's fonts. Renders on macOS on Intel and on Linux (x64 and arm64, glibc and musl) give the same bytes. Apple Silicon and Windows are not tested; if a render there differs, `docs:site:check` reports it. The fonts are Inter (Regular, SemiBold, Bold) and JetBrains Mono (SemiBold), static files under the SIL Open Font License 1.1, with the licence in `OFL.txt` next to each family. `tools/docs-site/fonts/README.md` names the release each file comes from and its SHA-256. The SVG may name only `Inter` and `JetBrains Mono` in `font-family` attributes. A `font-weight` or `font-style` without a vendored file renders with the nearest file. To use a new weight, add its static file from the same release (Inter 4.1, `extras/ttf/` in the release zip; JetBrains Mono 2.304, `fonts/ttf/`), list it in `scripts/og-image.ts` and in the README. `docs:site:check` renders the SVG again and fails when the committed PNG has other bytes, or when the SVG names another font family.
- The same PNG is the repository's social preview on GitHub, the image a link to the repository shows. GitHub has no API for it: the owner uploads it in the repository's Settings, General, Social preview, and uploads it again whenever the PNG changes.
- The favicon is `docs/public/favicon.svg`, with `docs/public/favicon-32.png` for browsers that do not show SVG favicons. The config adds a `<link rel="icon">` for each, with the base path (`/hardhat-kms/favicon.svg`), since VitePress does not add the base to head tags. The nav bar shows the mark, as [Logo files](#logo-files) describes.
- `sitemap.xml` lists every page with its last commit date, and `robots.txt` names it. Search engines read `robots.txt` only at the root of a host, `https://aelmanaa.github.io/robots.txt`, which this repository does not serve, so the sitemap has to be submitted in Google Search Console and Bing Webmaster Tools.
- `llms.txt`, `llms-full.txt` and a `.md` copy of each page come from `vitepress-plugin-llms`. After the build, the config rewrites the relative links of the copies and of `llms-full.txt` to absolute URLs on the site, since a copy is served at another path than its source (`user/reference/api/README.md` becomes `user/reference/api.md`) and `llms-full.txt` joins them all. The plugin gets the sidebar with the API pages lifted out of their nested group: version 1.14.0 drops the base path from the links of a nested group.
- `llms.txt` opens with a "Start here for agents" section, written in the config. It gives the install command per cloud, the `hardhat.config.ts` step and `npx hardhat kms accounts`, a reminder to check npm for the current version, and a link to the [install page](../user/guides/install-before-release.md) for pnpm and Yarn. That page kept its pre-release file name, `install-before-release.md`, when it became the install page, so its published URL still works: GitHub Pages cannot redirect. Once `skills/hardhat-kms/SKILL.md` exists, the section also gives `npx skills add aelmanaa/hardhat-kms`.
- The landing page carries a JSON-LD `SoftwareSourceCode` block, with the version and the Node.js range read from `packages/hardhat-kms/package.json` at build time.

To work on the site:

```sh
pnpm run docs:site:dev     # serve the site at http://localhost:5173/hardhat-kms/, with reload
pnpm run docs:site:check   # build the site, then check the output
pnpm run docs:og           # render docs/public/og-image.png from og-image.svg
```

`pnpm run docs:site:check` runs `scripts/check-site.ts`, in the CI Docs job on every pull request. The build fails on a link to a page that does not exist. The script then reads the output directory and fails when a page under `docs/` (contributor pages aside) was not built, or its head lacks one canonical URL without `.html`, the title suffix, one meta description equal to the frontmatter `description`, an Open Graph tag, an image tag that names the social preview's URL, size and alt text from `site.ts`, or a `<link rel="icon">` with the right type for each favicon; when a link or asset does not start with `/hardhat-kms/`, which a local preview would serve but GitHub Pages would not, does not resolve to a built file, or names an `#anchor` that the target page lacks; when `sitemap.xml` misses a page, `robots.txt` does not name the sitemap or `llms.txt` or `llms-full.txt` is missing; when a link in `llms.txt`, `llms-full.txt` or a `.md` copy is relative, leaves out `/hardhat-kms/` or names a file that was not built; when the landing page's JSON-LD is missing, invalid or carries another version; when the social preview is not in the build, is not a PNG, is not 1280x640 or is over 1 MB; when `favicon-32.png` is not in the build or is not a 32x32 PNG; and when `docs/public/og-image.svg` names a font family other than `Inter` and `JetBrains Mono`, or `og-image.png` differs from a fresh render of the SVG. `scripts/site-output.ts` holds the checks and `test/scripts/site-output.test.ts` their tests.

`.github/workflows/pages.yml` runs the same build and checks on every push to `main`, and on manual dispatch, then deploys the output with `actions/deploy-pages`. Only its deploy job has `pages: write` and `id-token: write`. GitHub Pages must be set to deploy from GitHub Actions (Settings, Pages, Source: GitHub Actions) before the first deploy succeeds.

### Logo files

The mark is a frame with a slot in its right wall, a solid block inside that is taller than the slot, and a green stroke that leaves through the slot. The block is the private key and the stroke is the signature: only the signature leaves the KMS. The files live in `docs/public/`, and VitePress serves them at the same paths under `/hardhat-kms/`.

| File                                                   | What it is                                                       | Use                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| `favicon.svg`                                          | The mark redrawn on a 16 px grid, on a navy tile                 | The site's favicon                                                  |
| `favicon-32.png`                                       | A 32x32 PNG of `favicon.svg`                                     | The favicon in browsers without SVG favicons                        |
| `logo/mark-on-light.svg`                               | The mark in light-surface colours, transparent background        | The nav bar logo in light mode                                      |
| `logo/mark-on-dark.svg`                                | The mark in dark-surface colours, transparent background         | The nav bar logo in dark mode                                       |
| `logo/mark.svg`                                        | The mark on its own navy tile                                    | Places with an unknown background, such as the npm README or slides |
| `logo/mark-mono.svg`                                   | The mark in one colour, `currentColor`                           | Inline SVG in HTML only: through `<img>` it renders black           |
| `logo/mark-mono-black.svg`, `logo/mark-mono-white.svg` | The mark in one fixed colour, black or white                     | One-colour use through `<img>` on light or dark pages, and print    |
| `logo/lockup.svg`, `logo/lockup-on-light.svg`          | The mark and the name "hardhat-kms", for dark and light surfaces | A README header, in a `<picture>` that follows the reader's theme   |
| `logo/avatar.svg`, `logo/avatar-400.png`               | The mark on a full navy square, safe for a circle crop           | Square avatars, such as a GitHub or npm organization's              |

`favicon-32.png` and `avatar-400.png` are exports of `favicon.svg` and `avatar.svg`. After changing either SVG, export it again at 32x32 or 400x400 and replace the PNG.

On a dark browser tab bar the navy tile's edge does not show; the lighter frame gives the favicon its outline.

Minimum sizes:

- The favicon files are drawn for 16 px. Use them, not a scaled-down mark, below 24 px.
- The mark and the lockups need at least 24 px of drawing height. The mark files pad the drawing, so the nav bar sets the logo to 34 px (`--vp-nav-logo-height`), which gives 24 px of drawing.

Keep the mark on its tile, or next to the project name, as in the nav bar and the lockups. On its own in a toolbar it can read as a log-out or export icon.

The social preview, `og-image.png`, has its own source, `og-image.svg`, described above. Changing a logo file does not change it.

Avatars are uploaded by hand: upload `logo/avatar-400.png` again whenever the mark changes.
